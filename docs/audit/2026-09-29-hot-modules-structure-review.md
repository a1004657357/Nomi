# 结构评审：四个热模块的根因合同为什么扎堆（2026-09-29）

> 状态：✅ 已评审，结论是结构性处置（收敛），不是再修一次。
> 触发：PR #924（存盘卡死修复）的 `check:symptom-cluster`。7 天窗口里的根因合同数：`electron` 6 份、`electron/assets` 8 份、`electron/capabilityCore` 7 份、`src/workbench` 38 份。同一天用户问「为什么老出现这种问题」。
> 依据：[`2026-09-26-architecture-single-owner-governance.md`](../plan/2026-09-26-architecture-single-owner-governance.md)（#897）与 [`2026-09-26-phase-zero-cluster-index.md`](2026-09-26-phase-zero-cluster-index.md) 的七个结构簇。

## 结论

这四个模块不是四个各自独立的结构问题。它们都落在 #897 已经定过的同几类根因里：

- 两台生成发动机：画布直生成和 ProductionRun；
- 同一件事多处判断；
- 跨边界约定没有共用定义；
- 投影层自己下结论；
- 失败不出声。

按合同逐件修，只能把一个入口接回正确的零件，别的入口照旧保留旧判据，所以合同会继续出。结构上的处置是收敛，用户 2026-09-29 已拍板「现在并行开工」。0.23 只修两类：「用不了」和「花钱错」，而且只修在收敛后还会保留的代码里。

## 各模块的簇与归因

### `electron/assets`（8 份）
合同：
- 导入时的 Windows 共享冲突、构建产物地址写进项目数据、素材名保住扩展名 → P0-5；
- 参考图误判 → P0-4；
- APIMart 制作边界 → P0-4 / P0-1；
- Agent Run 节点状态 → P0-1 / P0-2；
- 视频播放器常驻 → P0-2；
- 今天的取回存活 → P0-5 / P0-4。

共同点：「取回 → 校验 → 落盘 → 发布」这一段现在有好几个入口，包括画布渲染层补落地、制作落地、导入、Agent。每个入口的时限、校验、命名各写一份，所以每次都只修好一个入口。

今天的修复把取回预算收成一个 owner（`electron/shared/assets/providerMediaRetrievalBudget.ts`），把「放弃响应」收成一个出口（`hardenedFetch.ts` 的 `abandonResponse`）。剩下的问题是「落地」仍然从两台发动机进来。这要等收敛 Phase 2 把画布直生成接进 ProductionRun 的产物接缝（artifact seam）才能消掉。

### `electron/capabilityCore`（7 份）
合同：Agent Run 节点状态、素材扩展名、生成变体、分镜供应商拒收、画布媒体宽高、MCP 被动请求冷启动、今天的取回存活。

共同点：capabilityCore 承载 ProductionRun 和 Agent / MCP 的生成接缝，而画布直生成绕开了它。两边都需要的事实（变体、参数、宽高、节点状态）因此各判一次，属于 P0-1 双生命周期，外加 P0-4 合同分叉。

### `electron`（6 份）
合同：
- ComfyUI 连线类型 → P0-4，外部格式；
- 清单锁的 Windows 共享冲突 → P0-5，存储环境；
- 渲染层失败证据 → P1-7；
- 第三方媒体 COEP → 跨源边界；
- MCP 被动请求冷启动 → P1-6；
- 今天的取回存活 → P0-5。

`electron` 是顶层目录，把不相干的子系统聚到了一起，同目录不代表同一个缺陷。共同的线是两条：
- 跨进程 / 外部边界没有共用约定；
- Windows 存储环境。#897 已把它登记为 `storage-environment contract` 残余风险。

### `src/workbench`（38 份）
三大组：
- **生成 / 制作投影**：Agent Run 节点状态、画布生成无视制作镜头、在途镜头重开显示、任务中心状态、付费确认、模型目录读取、变体 → P0-1 / P0-2。渲染层是两台发动机的事实被投影、再被重新判断的地方，所以合同最多。
- **画布交互**：拖拽指针过滤、rAF 兜底、节点拖放丢失、连线环、分组连线环、锚定放置、自动视角、输入框钉位 → P0-2，属于手势寿命和缩放多 owner。这一组不靠生成收敛解决，对应 #897 Phase 1 准入条件里「画布缩放五个 store 的直接读取者迁移」和 React Flow 单内核规则。
- **Agent / 技能**：技能显示名、工具名单过期、代码块皮肤、lane 身份 → P1-6。

### `electron/productionRun` 与 `electron/shared`（为接下来的 #921 等预先点名）
ProductionRun 是收敛后留下的那台发动机。镜头认领（#921）、草稿镜不说排队中、定妆照检查点后授权版本对不上，都是 P0-1 两台发动机之间的接缝补丁。2026-09-29 起它们是最后一批接缝补丁：不再新增，收敛 Phase 2 把画布直生成接进来以后，认领这类跨发动机判断就没有存在的必要了。

## 为什么逐件修止不住：今天的实证

2026-09-29 #921 的真额度验收：
- 删节点的上报格式过不了主进程 IPC 校验，渲染层 `catch {}` 把拒收吞掉，一个多月没人知道。测试绕过 IPC 直接写仓库，所以是绿的。
- 派发前认领闸排在「提交意向落盘」之后，形同虚设。单测用的前提状态和真实调用顺序不符。
- 零花费彩排有一次请求漏到真供应商。

实扫 `src/` 有 46 处空 `catch`，其中约十处在花钱或存数据的路径上。

这些说明两件事：测试证明的是「代码以为的路」，而不是用户真走的边界；失败不出声，问题只能拖到真额度验收才暴露（P1-7）。

## 结构处置

1. **收敛 Phase 1（2026-09-29 已开工）**
   - `check:concept-owners`：同一概念出现第二个写口就红；
   - 把 2026-09-26 之后新长出的 owner 登记进 `docs/engineering/concept-owners.json`；
   - 耐久提交与崩溃恢复骨架；
   - 旧路径红测。
2. **收敛 Phase 2 第一刀**：画布付费生成接进 ProductionRun。它消掉的是 `src/workbench` 与 `electron/assets` 合同最大的来源，即画布直生成那条生命周期。
3. **现在就做的横切项**
   - 空 `catch` 棘轮：新增即红，花钱和存数据路径上的逐个改成会报错；
   - 花钱路径的改动，合并前必须有按用户动作走过真 App 的验收收据；
   - 绕过真实边界的测试（直接写仓库、跳过 IPC 或校验层、前提状态和真实调用顺序不符）不算证据。
4. **直到 Phase 2 落地前**，这几个模块的新修复要在根因合同里写明属于 #897 哪个结构簇，不许引入第二个 owner（R33）。「用不了」「花钱错」以外的修复排到收敛之后。
