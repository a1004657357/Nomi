# 结构评审 · 付费确认这一层（`electron/capabilityCore` / `src/workbench`）

- 触发：`check:symptom-cluster` —— `electron/capabilityCore` 在 2026-09-15 到 2026-09-21 的 7 天里收到 23 份根因合同，`src/workbench` 3 份。第三份合同是「这一层的结构不对」最便宜的证据。
- 范围：本文只评审**付费确认那条链**（Agent 面板付费卡 → IPC → `appIntegrationSpendConfirm` → `decideGenerationSpend` → 供应商），以及它的验收方式。`electron/capabilityCore` 这个簇里其余合同（分镜、画布落地、MCP 投影等）不在本文的证据范围内，需要另一轮。
- 证据全部来自 2026-09-21 Pass 3b 的真机实测（零额度，供应商是本机 loopback 夹具），不是读码推断。

## 一、这一层今天真正的形状

付费确认本身是**收敛的**：四个动作（读 / 改参数 / 丢弃 / 确认）共用一个编排、一个失败出口；「封印 → 铸收据 → 决门 → 消费 → 开跑」只有一条实现，全自动档走的也是同一个函数。这一点值得说清楚，因为它和簇的大小给人的印象相反：**合同多不等于这条链是碎的**。

碎的是它**周围**的三件事，而三件事是同一个形状：**一个语义被两处各自回答，两处都不报错。**

| # | 语义 | 主人（今天） | 第二个答案（今天） | 后果（实测） |
|---|---|---|---|---|
| 1 | 「这个模型有哪些参数」 | 档案 `src/config/modelArchetypes/*`（渲染层照它画控件） | `moduleCatalogBootstrap.modelParameterSchema`（只从 `onboarding.fields` + `mapping.create.defaultParams` 派生） | 内置目录 248 个 mapping 只有 12 个带 `defaultParams`、156 个模型 0 个有 `onboarding` ⇒ `executionContract.compileParameters` 把用户在卡上改的参数**整包丢弃**，线缆跑 `archetypeWireDefaults` 的默认值。实测：卡上选 2K，供应商收到 `resolution: 1k`，而画布节点上印着 2K。 |
| 2 | 「这一笔有没有离开过这台机器」 | Run 账本（作业状态） | `failed()` 的一句兜底话（`generation_execution_failed`） | 用户读到「暂时无法确认这一步的结果」——在「根本没发起」时是误导，暗示可能已扣费，于是不敢再按、转而去找一个不存在的任务。**本次已修**：按账本分 `generation_not_started` / `generation_execution_failed`。 |
| 3 | 「这条走查接不接得到生产路径」 | `generationProviderBootstrap`（只装 apimart） | 每份走查文件头的一段注释（「这条走查证不到产物落回节点，这是有意的」） | 三条走查把一次**拒绝**当成通过，一路带到发版前；`main` / PR #828 head / 本分支的 bootstrap 是同一个 blob，所以这是长期状态而不是回归。**本次已修**：启动口上一个显式开关 + 机器可验的事实断言。 |

## 二、判断：是不是结构问题

是，但不是「付费确认这一层要重构」。三条都长成同一句话：**一个语义没有主人，于是每个需要它的地方各自重新回答一遍，而重新回答不会报错。**（与 `memory` 里 09-18 那条「958 个声明过的 owner 没人核」同形。）

区别只在重新回答的方式：
- #1 是**重新解释**（档案说有这个参数，合同说没有）；
- #2 是**重新计算**（账本知道答案，话术自己编了一个更保守的）；
- #3 是**用注释代替判据**（缺口被写下来了，但没有任何机器读那段注释）。

## 三、下一刀（按代价从小到大，不在本轮做）

1. **把 #1 的主人钉死**：`modelParameterSchema` 应当从档案派生，而不是从两份几乎空的目录字段派生。收益：用户在卡上改的每一个参数真的会到线缆上。风险：涉及全部内置模型的出站载荷，必须先有逐档案的对照测试，属架构裁决，需主会话拍板。今天的表现是「你批准的是 A，我们生成的是 B」——这在花钱这条轴上不该过夜。
2. **把 #3 做成棘轮**：任何断言「真的生成了」的走查必须声明它跑在哪一档供应商上；跑在自造供应商上却断言生成 = 门岗红。今天靠的是这一轮把三条改对了，没有东西拦住第四条。
3. `electron/capabilityCore` 那 23 份合同还需要一轮真正的横扫（本文没有覆盖）：建议按「哪一个语义被重新回答了」分桶，而不是按症状分桶——本文这三条就是这么找出来的。

## 四、本轮据此做了什么 / 没做什么

- 做了：#2 与 #3（见 `docs/fixes/2026-09-21-spend-confirm-never-generated.root-cause.json`）。
- 没做：#1。它不是本轮那个发版阻断项，改动面涉及全部内置模型；已记入该合同的 `residual_risks`，等主会话裁决。
