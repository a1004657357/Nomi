## 三个结构性缺陷（都是真额度换回来的，不是预设用例）

### A. I2V 两跳在主力视频模型上**从来没触发过** —— W2 的招牌功能是死的

`shouldUseTwoHop` 用**手写正则**猜「这个模型有没有首帧槽」：`/first_frame|firstframe|start_image|image_url$|^image$/i`。
Seedance 的 i2v body 用的是 `image_urls`（复数）——`image_url$` 要求以 `image_url` 结尾，**匹配不上**。

实测（不是读代码推断）：Seedance 2.0 derive 出的 10 个参数键
`audio_urls, duration, generate_audio, image_urls, image_with_roles, model, resolution, seed, size, video_urls`
**没有一个命中**。Kling 的 `first_frame_image` 能命中，主力的 Seedance 命中不了。

**后果被这一轮量化出来了**：两跳不跑 → `ffDesc`（分镜精心写的静态场景描述）一个字都用不上 →
**4/6 镜场景漂移**。#2/#6 身份满分（锚图直接进了 i2v 参考通道）但场景错（描述没送达）——
身份和场景在这里是两条独立的通路，只有一条通着。

**更深一层**：Seedance 的首尾帧槽其实是 `image_with_roles: [{url, role:'first_frame'|'last_frame'}]`，
而我们的投影发的是 `first_frame_url`。**即使判据修好让两跳触发，那张首帧图也到不了 Seedance。**

**根因不是「正则漏了一个 s」**——是拿手写模式去猜各家键名，下一家换个叫法照样漏。
目录里本来就有 derive 好的参考承载力（`bodyReferenceSupport` / `referenceModeForIntent`，`list_models` 用的同一份源）。
判据该问那份，不该自己再写一套。

**连带**：上一轮 L3-W2 报告里「② I2V 两跳真跑」的结论**是错的**——同一个模型，同样没触发；
我把判分抽出来的帧当成了两跳的产出。已在本报告更正。

### B. 审片环对视频**只看第 1 帧** —— 造成误报 + 对头号失败模式失明

`extractFrame` 只问 `which:'first'`。而「逐渐显出 / 由暗转亮 / 缓缓推近」是短剧最常见的镜头语言。

三层后果，本轮全部实地撞上：

1. **误报**（#5）：那一镜的设计就是「远处路灯下**逐渐**显出背影」。判分器在 t=0 看，什么都没有 →
   构图 1 档 → 重滚一次 → 仍 1 档 → 红标。**而尾帧里人影明明出现了。** 红标是信任的基石，
   误报和漏报一样毁它——用户被告知「你这镜坏了」，其实好得很。
2. **白烧额度**：那次重滚是为一个不存在的问题付的钱。
3. **对「动到一半人就变了」完全失明**：这是视频生成的头号失败模式，而判分器结构上看不到。
   本轮两条带锚镜没有漂移——**但那是我手动抽尾帧验的，系统不知道。**

能力本来就在：`extractVideoFrame` 支持 `first | last | 秒数`（文件头注释白纸黑字写着），只是没用上。

### C. 连贯轴从来没评过（本轮已修，待验）

全 6 镜 `continuity=—`。`previousShotPrompt` 从没被传过——headless 每次 `nomi_generate` 都是独立调用。
**审片环对外说三轴，实际只跑了两轴**，而「接不接得上」恰是短剧最容易崩的那轴。

上一镜可从 `shotIndex` derive，不是拿不到。已补 `previousShotPromptFor`（判不出就返回空，
不拿错的镜去比——错参照物比不比更糟，会凭空判出断裂再触发白烧的重滚）。**本轮跑的是修之前的包，待复验。**

## 缺陷 A/B 已修（同日）

**A — 两跳判据改用目录 derive**（commit `9d0b233a`）：不再手写正则猜键名，改问目录里那张经实战打磨的
参考键族表（`referenceReachability.REFERENCE_KEY_FAMILY`，`list_models` 用的同一份源）。
另补上真正让两跳有意义的那半：**两跳成了 → 参考通道换成那张首帧静帧**，不再发原始锚卡——
锚卡是中性灰背景的证件照，拿它当 i2v 驱动图等于让视频从证件照开始动；静帧已经长成这一镜该有的样子
且身份已由锚卡锁定，同时携带身份与构图。

尾帧仍按键名匹配（族表把首/尾帧都归 image 族，区分不出「指定尾帧的位置」），并如实记下：
Seedance 用 `image_with_roles` 角色数组表达首尾帧，匹配不上 → 不出尾帧图。**这是故意的**：
我们的投影发 `last_frame_url` 本来也到不了它，宁可不生成也别烧一张送不到的图。

**B — 视频判分改看首尾两帧**（commit `592d58d2`）：视频镜喂给判分器的改成首帧+尾帧的横向拼图
（复用既有 ffmpeg 基建，单次调用双 `-ss` 输入 + 等高缩放 + hstack；实测真视频 720×1280 → 812×720，
确是并排）。rubric 同步告诉判分器「这是首帧(左)与尾帧(右)」且**内容随时间展开是正常的、不要只看左边**——
不说这句，拼图只会让它把右半才出现的东西当穿帮，比不拼更糟。identity 轴加一条「同时比较左右两帧
是不是同一个人」，把中途变脸纳入可检测范围。

**测试没有为了过而放水**：既有那条「不读首帧键 → 只发一次」的夹具用的其实**是**图片参考通道
（`reference_image_urls`），它固化了错误行为。没改断言了事——把夹具换成真正的纯文生 body 保住原意，
另加两条哨兵（core 层「数组式参考键照样两跳 + 第 2 跳参考换成静帧」、纯核层「用实测 dump 的
Seedance 真键名」——编的键名当初就是这么骗过自己的）。

## 复验结论（2026-08-20 · 见 `docs/audit/2026-08-20-l3-f1b-reverify/report.md`）

**A/B/C 三缺陷全部修好，且眼见为实。** 但 A 追了三轮——每修一层才露出下一层：

1. 键名正则匹配不上 `image_urls`（`image_url$` 要求以 image_url 结尾）→ 修完**仍不触发**；
2. 第 1 跳**拿视频模型去画图**（`findExecutableModel` 按 kind 过滤必然失败，错误被 catch 吞掉）
   → 修完**仍不触发**；
3. 画师是**异步 vendor**，首调只返 taskId、没有 assets，而首帧那跳**从不轮询** → 永远判「没出图」。

三层都只有真机能暴露：单测的 `runTaskFn` 是桩，桩不管你要什么 kind 都同步还你一张图，
既不会因 kind 过滤失败，也不会 queued。**这正是 L3 在三层验收体系里不可替代的地方。**

修完后的首帧静帧我逐项对过 ffDesc：深夜便利店 ✓ 低头理货 ✓ 腰部以上中景 ✓ **冷白顶光**（灯管
就在画面顶上）✓ **背景货架与冰柜** ✓ —— 每一项都落地，**场景漂移消失**。视频尾帧是同一场景同一人，
抬头动作完成——那张静帧真的驱动了视频。

**判据⑦ 仍不算过**：复验为省额度只跑 1 镜，1 镜的分母下不出结论。要等一轮完整多镜跑。
