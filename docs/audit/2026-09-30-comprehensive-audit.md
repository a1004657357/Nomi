## P0：凭据随跨源重定向泄漏（已修复）

### 证据链

1. 所有 Node 出站请求都经 `electron/appFetch.ts`；它把调用方的选项原样交给原生 `fetch`，而原生默认跟随 302/307/308。
2. 跨域跳转时，标准只会去掉 `Authorization`；`x-api-key`、中转站自取名的鉴权头会原样带到第二个网站，307/308 还会重放 POST 正文。
3. 出站守卫（`electron/vendor/vendorOutboundGuard.ts`）只校验初始目的地，看不到后续跳转的 origin。
4. 当时只有少数调用点自己写了 `redirect` 选项，其余（供应商传输、接入向导协议探测、AI SDK、multipart 与音频上传等）都没有。

本地双端口复现：源端口返回指向另一端口的 302、307 或 308。默认跟随后，目标端口可收到自定义鉴权头；307/308 还会保留 POST 正文。该复现不需要真实供应商或真实凭据。

### 修复

- 规则只判一次，住在 `electron/credentialRedirectPolicy.ts`：请求带了标准头（Accept、Content-Type、User-Agent 等）之外的任何头，就算带凭据，使用原生 `redirect: "error"`，不自己写跟随逻辑。供应商的鉴权头名是配置出来的，按名字拦黑名单会漏，所以不认识的头按带凭据处理。
- `appFetch` 是唯一出站入口，由它应用这条规则；各调用点不再各写一遍。调用方自己指定了 `redirect`（逐跳去头的 `hardenedFetch`、手动分页并校验的模型列表）时尊重它。
- 单测的传输替身同样应用这条规则，领域测试不会跑在比生产更松的策略下。
- 失败时给人话，不再是一句 `fetch failed`：生成路径走既有失败分类（新增 `credential-redirect` 码和词表条目，中英文），接入向导与音频转写走桌面端文案表。文字告诉用户服务商地址发生了跳转、为保护密钥已停止，并让用户把地址改成跳转后的最终地址。该提示不声称「没有扣费」，因为请求已经到过用户配置的地址。
- 新增真实本地 HTTP 双端口回归（`electron/credentialRedirect.test.ts`）：用真实的 `appFetch` 对 302/307/308 走四个入口，断言第二个端口零请求、零鉴权头、零敏感正文；并验证不带密钥的普通下载仍会跟随跳转。

### 已知限制

- 除模型列表拉取（手动模式，拿得到 Location，提示里会写出跳转目标）外，原生 `fetch` 只报告「发生了跳转」，不给出目标地址，所以其余入口的提示没有写出跳转后的地址。
- 只有 URL 查询串或正文里带密钥、而没有任何非标准头的请求，不被判为带凭据。

## 其他高优先级发现与方案

| 优先级 | 发现 | 具体解决方案与验收 |
|---|---|---|
| P1 | 批量取消存在竞态：取消、超时或新一轮结果到达的顺序可能让旧结果回写节点或消费记录。 | 在批次和节点写回处使用 fencing epoch/operation id；取消后拒绝迟到结果，提交、回写和消费记录做同一事务边界。补充取消与迟到响应交错的真实 loopback 测试。 |
| P1 | `localStorage` 备份清理、恢复和并发写入的组合路径仍可能互相覆盖，配额失败后恢复证据不足。 | 使用单一 journal/CAS 写入门；备份按版本保留并在恢复后校验校验和；清理、恢复、并发保存和冷启动各有故障注入测试，任何失败都要返回可行动状态。 |
| P1 | registry JSON 损坏时存在启动解析抛错风险，可能让整条能力注册链退出。 | 解析失败时隔离并重命名坏文件，加载安全空快照并把状态标为 `unavailable`；记录脱敏原因，不能静默当成空注册表。 |
| P1 | Agent/Skill 刷新顺序可能先发布工具面再发布 skill 快照，短窗口内出现旧 skill 指针配新工具目录。 | 用单调 snapshot generation，在 skill、工具和能力投影全部就绪后一次性发布；刷新期间保留上一份一致快照，增加并发刷新顺序测试。 |
| P1 | 未知任务状态被 UI 默认显示为 queued，掩盖了需要 reconcile 的状态。 | 状态投影采用显式 `unknown`/`needs_reconcile`，禁止未知值落到 queued；界面给出可操作的恢复或重新查询动作，并为未知枚举加契约测试。 |
| P1 | multipart/音频出站路径是否绕过统一出站策略。 | 已由本 PR 的 P0 修复覆盖跳转这一面：multipart 与音频上传都经 `appFetch`，同一条规则生效。仍待做的是「未登记的 operation 在发出请求前拒绝」，单独跟进。 |

## 排序与后续验收

1. **已完成（本 PR）**：关闭 P0 跨源重定向凭据泄漏，规则放在最早的共享出站边界，并给用户一句看得懂的话。
2. **下一项 P1**：先收口批量取消的 epoch/fencing 与迟到结果写回，再做 localStorage journal/CAS；两项都需要故障注入和冷启动证据。
3. **随后 P1**：修复 registry 损坏隔离、Agent/Skill 原子刷新、未知状态投影，以及未登记 operation 的发出前拒绝；每项完成后重新跑合同门和相关领域套件。
4. 合入前必须补打包态冷启动和国内无代理网络证据；若仍受环境阻塞，应在交付记录中保留 `blocked`，不能改写为通过。
