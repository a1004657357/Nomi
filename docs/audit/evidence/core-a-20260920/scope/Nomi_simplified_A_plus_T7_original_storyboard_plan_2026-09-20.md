## 3. 新流程的接线、目标和冲突规则

### 3.1 目标捕获与状态分工

捕获对象的语义必须包含：真实项目执行身份、`documentId`、`designId`（创建前用现有请求身份防重复）、稳定镜头／锚点 ID、实际来源版本与预期方案内容版本。字段使用当前共享类型；本文件不另造 `TaskContextManager` 或新的全局状态机。

捕获与校验分别执行：发起时锁定“用户在操作什么”，提交时核对“这个身份现在仍有权限、对象仍存在、版本是否变化”。只切同项目的可见文稿／方案，不应把写目标换掉；若原权限允许，结果写回原目标且不抢新焦点。切换项目导致原执行身份失效时，停止相关写入或由既有受信宿主持有原任务完成；不得给新项目重签身份继续旧动作。

目标被删除：返回缺失，不创建替代方案。内容已变化：返回冲突，保留双方内容与用户未保存文本；不要 last-write-wins，也不强制 refetch 丢本地草稿。冲突校验必须位于实际写入处，不是只在发送按钮前检查一次。不要把项目全局 `persistRevision` 无条件当成方案内容 CAS，让无关进度更新制造假冲突。

### 3.2 逐步流程

| 步骤 | 读哪份数据 | 写哪份数据 | 目标／冲突／副作用要求 |
|---|---|---|---|
| 新建空白方案 | 原文稿与既有方案列表 | 经 I1–I3 核实的目标方案存储 | 生成稳定新方案 ID；零 LLM／媒体请求；不替换用户编辑过的空壳 |
| 从当前文稿交给 Agent | 发送时指定的文稿内容及版本、必要技能与引用 | 先进入原输入／队列；完成后经 I4 写指定方案 | 全文读取不拼混版本；新建与修改语义分开；不重读当前焦点决定归属 |
| Agent 修改某方案／第 N 镜 | 真实方案 ID＋发送时对应的 shotId | 同一方案的获准写口 | 不改最近 Run、同名方案或新的选中项；重复回包不重复创建 |
| 原编辑器打开 | I2 的同一方案对象 | 不因打开就写数据 | 原表、参考槽和参数照常可用；模型未加载不清空已存模型身份 |
| 编辑标题／prompt／参考／参数 | 当前编辑所基于的 plan 与目标版本 | I3 的同一保存对象 | 显式传文稿和方案；不保存一份缩减到纯 prompt 的影子对象 |
| 保存进行中切换 | 原动作捕获的目标与待保存内容 | 原目标或准确冲突 | 不清新页面草稿、不抢焦点；“已保存”只在真实持久成功后出现 |
| 项目关闭和重开 | 原项目保存的方案、引用和节点绑定 | 原恢复路径；读取本身不运行生成 | 重建原读模型，不重新编译创建节点，不用当前缺模型覆盖历史参数 |
| 查看画布 | 已绑定节点与布局 | 仅原导航／定位状态 | 只查看不 materialize、不更新 plan、不弹付款卡 |
| 原生成／落画布动作 | 原 plan 与既有节点绑定 | 缺失节点＋允许投影字段；执行仍走原 runner | 重复进入不重复节点；不得另加“必须先落画布”步骤 |
| 单镜／×3／首帧／批量 | 同一目标对应的原动作输入 | 原确认与执行系统 | 只执行用户实际批准的集合；首帧依赖及 ×3 次数保持原语义 |
| 关闭付款卡 | 这张卡的请求身份 | 仅本次待批准请求状态 | 零新媒体提交；方案和节点保留；不把关闭等同显式删除 |

**“落画布”是原按需节点创建能力，不是要恢复一个新的确认门。** 固定基线已让行内／批量生成按需建节点，不应为了本次接线再要求用户经历新的编译、确认落地、执行选择页面。

### 3.3 编辑适配与保存字段

保留原 `StoryboardPlan` 语义：镜头稳定身份、顺序、类型、prompt、时长、整片默认和逐镜覆盖、模型／供应商／模式、参数、keyframe、anchorIds、引用槽和素材身份。当前 plan 还有其他受支持字段时也需往返保真，不按本清单截断。

保存要区分三类数据：

| 数据 | 正确位置／行为 |
|---|---|
| 作者内容 | 原目标方案的实际保存对象；参考和参数不能只存到临时 UI |
| 画布布局、结果和明确覆写 | 原画布数据及覆写机制；不从方案全量覆盖 |
| 付款／执行记录 | 原 runner／ProductionRun 已有合同和结果；不因编辑器保存而新建批准或执行 |

`sourceDocumentUpdatedAt` 用作来源信息，不能在编辑 prompt 时随手改为此刻另一文稿的时间；它也不独立证明内容版本相同。`syncSource`、`createNew` 等原参数必须按本次动作语义使用，不当万能修复开关。版本、绑定元数据若已有持久化入口就修那个入口；不得因此新增第二套“保存元数据数据库”。

### 3.4 重复落画布与覆写保护

复用 `storyboardNodeBinding.ts` 的方案／镜头／首帧／锚绑定；调用前处于正确项目和文稿范围。稳定 ID 不因镜头重排、标题变化或页面重开而重发。旧索引或同名兼容规则不可扩展为新写入的身份依据。

原 `projectShotNode` 处理内容与覆写；检查它对首帧、参考槽等实际受影响字段的行为，不因“原代码”就免测。重复查看／落地不能把画布用户改过的 prompt、参数、参考、布局、结果 URL、历史堆叠或任务状态覆盖回初稿。

现有节点能复用就复用，只有用户明确需要且确实缺失的节点才创建；并发 materialize 必须利用现有提交边界保证同一绑定不被创建两次，仅有组件 `busy` 不能作为跨调用者的充分保护。缺一个首帧或锚点时，也不能顺手重建已经存在的镜头本体。

需要将更新后的方案字段投影到已有节点时，仍走原明确编辑／执行动作与覆写规则。纯查看或 hydrate 禁止触发；不要以“为了安全”永久停止原来合法的方案投影，更不要提供一个新执行系统绕开原行为。

## 4. 现有施工如何处置

### 4.1 先拿完整差异，不按文件名下结论

本地实施 AI 先在用户指定 core-a 工作区读取：

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git rev-parse 'HEAD^{tree}'
git worktree list --porcelain
git diff --no-ext-diff --no-textconv --name-status
git diff --cached --no-ext-diff --no-textconv --name-status
git ls-files --others --exclude-standard
```

然后读取两个用户点名的 execution／structure-review 文件；将历史误判标出来，不把它们凌驾于最新要求或实际代码。

完整审查集合＝经核实的任务基线到 HEAD 的提交差异＋HEAD 到工作树的净 tracked 差异＋各相关 untracked 文件内容。另查看 staged／unstaged 来源用于保护未提交施工；不要把相同差异重复计数。记录 rename/delete 和共享类型／调用者依赖。普通 `git diff` 不会自动包括全部新文件；只看 diffstat 不能完成处置审计。

Git 原始补丁可能包含私人内容，留本地受控目录；对外只传用户允许的源码／脱敏记录。上述命令不授权读取 key/profile/私钥或发送它们。不得 reset/clean/整文件 checkout、整树回滚或把其他 session 的修改自动 stash。

### 4.2 逐增量清单的必填列

`文件与符号 → 来源基线/增量hash → 当前作用 → 用户要求/原A/T7归属 → 读取与写入对象 → 调用者/依赖 → 保留/调整/撤除 → 具体理由 → 替代接线 → 测试 → 提交`。

这张表由实际 diff 生成。未读到的项标“待核查”，不能填“保留”当安全默认，也不能填“撤除”当默认简化。**待核查是证据状态，不是第四种最终处置。** 最终每个本轮生产增量必须有三选一结论；无法获取代码时明确保留审计缺口。

### 4.4 安全撤除顺序
