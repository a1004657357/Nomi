# 结构评审 · Pass 3e 的四个合同簇（2026-09-21）

> 触发：`check:symptom-cluster` 在四个模块上同时报「7 天内第三份根因合同」——
> `electron/catalog`、`electron/providerAdapter`、`scripts`、`src/i18n`。
> 门岗的原话是「第三份合同是『这一层的结构不对』最便宜的证据，不是再修一次的理由」。这份评审回答的就是
> 那句话：这四个簇里，**哪几个真的是结构不对，哪几个是尺子的形状不对**。
>
> 材料：本轮（Pass 3e）四条阻断的根因调查 + 两轮横扫（`sweep-one-intent-many-engines.md` /
> `sweep2-entrypoint-completeness.md`）+ 这四个模块下 2026-09-15 起的全部合同。

## 〇、一句话

四个簇里只有两个是「这一层的结构不对」——`electron/catalog` 与 `electron/providerAdapter`，
而且它们是**同一个**结构问题的两半。另外两个（`scripts`、`src/i18n`）是尺子的问题：
它们不是层，是**几乎每次改动都会顺手碰一下的叶子**，所以合同数只反映改动总量，不反映结构质量。

## 一、`electron/catalog` + `electron/providerAdapter` —— 真的结构问题：一条连接的「完整说法」没有持有者

这两层在合同上的形状是重复的，而且两轮都撞在同一个地方：

| 日期 | 合同 | 丢的是什么 |
|---|---|---|
| 2026-09-18 | `vendor-upsert-drops-fields` | **写路**：重建一条 Vendor 记录时用白名单式**保留**，没列到的字段（`authScheme`、`assetIngestion`）静默消失 |
| 2026-09-21 | `auth-scheme-dropped-on-read-paths`（本轮） | **读路**：同一个 `authScheme` 在「列模型 / 模型发现 / 测试连接」三处根本没有传下去的位置 |
| 2026-09-21 | `background-reconcile-disables-user-models`（本轮） | **归属**：供应商清单这条观察，被允许去写用户自己的 `enabled` |

三份合同的共同形状不是「谁手滑了」，是 **一条连接记录没有一个「完整说法」的持有者**：

- 它的字段被**逐个**在各处手抄（写路抄一遍、读路抄一遍、探测路再抄一遍）。少抄一个在语法上永远合法，
  所以每加一个鉴权/接入维度，就会在某一条路上静默丢一次。本轮把「一把 key 怎么放」收成
  `VendorAuthSpec` 值对象 + `catalog/vendorAuthSpec` 单一 owner 之后，收紧签名的那一刻编译器
  一次报出 7 处——**其中一处（`modelListProbe.buildAuthHeaders` 自己写死 `Bearer`）是两轮横扫都没发现的**。
  这就是「结构不对」的直接证据：靠人读读不出来，靠类型一秒报出来。
- 它的字段**没有归属轴**。`enabled` 是用户的决定，`unlisted` 是我们的观察，`authScheme` 是供应商的事实——
  三种寿命完全不同的东西平铺在同一个 `Model`/`Vendor` 上，于是「谁能写它」全靠注释约定
  （`seedBuiltins.ts` 里那句「种子不碰 enabled（那是用户数据）」的下面三行就在写 `enabled: false`）。
  这与 09-17 的所有权/寿命审计（`ownership-lifetime-audit-20260917`）指出的是同一件事：契约缺「寿命」轴。

**结论（这一层该怎么改，不是再修一次）**：给连接与模型记录补两件事，各自一刀，别跟在下一个 bug 后面做。
1. **完整说法**：`Vendor` / `Model` 的每个字段都要么进一个值对象（像本轮的 `VendorAuthSpec`），
   要么进一张「新增字段必须有一条裁决」的登记表（`check:framework-surface` 已有这个形状，本仓自己的
   记录还没用上）。判据：新增一个字段时，**编译器**在全部消费点报红，而不是等用户 401。
2. **寿命轴**：给每个字段标 owner（user / observation / provider-fact），并让写入口按 owner 收口——
   观察类字段的写入口不许出现用户字段。本轮在 `modelListReconciliation` 的返回类型上做了一个单点示范
   （类型里没有 `enabled`，这条边界就写不了它），把它推广到整张记录是下一刀。

**别做的**：不要再用「后台任务小心一点」「注释写清楚」这种办法。这一层已经有两处注释与代码互相矛盾了。

## 二、`scripts` —— 不是一层，是每份合同都会引用的叶子

22 份合同在 7 天里点到 `scripts`。逐份看，绝大多数的 `scope_paths` 里的 `scripts/*` 是
**门岗脚本或走查脚本**（`check-*.mjs`、`tests/ux/*`、`scripts/nomi.mjs`），即：
「我修了一个 bug，顺手给它加了一条门岗/走查」。本轮我自己的那份
（`legacy-canvas-write-doors`）也一样——它点到 `scripts/nomi.mjs` 是因为**删掉了**那条 CLI 的四个写子命令。

也就是说这个簇的计数反映的是「这一周做了多少带门岗的修复」，不是「`scripts/` 的结构不对」。
`scripts/` 下面没有共享的领域不变量，每个门岗各管一条，彼此之间不应该也没有耦合。

**唯一一条真的结构观察**：`scripts/nomi.mjs` 这类「给人用的本机 CLI」与「给 AI 用的 MCP 语义面」
长期是两套能力清单，而前者走的是裸 bearer。本轮删掉它的画布写子命令正是因为这个——
**裸 bearer 证不出「哪个客户端、哪次会话、哪个项目」**。建议把这条写成纪律：
`scripts/nomi.mjs` 只保留只读与项目级动作，任何会改项目内容的能力一律只在语义面上。

**对门岗本身的建议**：`check:symptom-cluster` 的模块轴应当排除 `scripts/`（和 `docs/`、`tests/`），
或者只统计 `scope_paths` 里**不是**门岗/测试的那些路径。否则它会稳定地在这里报一个永远修不掉的红，
而「稳定报红且修不掉」的门岗最终会被人加进忽略列表——那才是真正的损失。

## 三、`src/i18n` —— 同上，而且更纯粹

5 份合同点到 `src/i18n`（本轮我一份都没有；它是 Pass 3a/3c 留下的）。原因很直接：
**凡是用户可见的修复，都要动 zh/en 两份词条**（R15 硬零，不动才不正常）。
所以这个簇的计数 ≈ 这一周有多少条用户可见修复，与 `src/i18n` 的结构无关。

`src/i18n` 自己的结构问题另有其事，而且已经各自有门岗与合同在管：
动态拼键的可解析性（`2026-09-03-dynamic-i18n-member-gate`）、展示名该在哪一层翻译
（`2026-09-02-i18n-display-name-boundary`）、死词条的两种成因。这些都不是「同一层反复出 bug」，
是不同的问题各出一次。

**建议同第二节**：把 `src/i18n` 一并排除出模块轴，或按「这份合同的 `class_root` 是否发生在这一层」
而不是「`scope_paths` 是否碰到这一层」来归簇。今天的归簇用的是后者，于是**被顺手改到的层**
和**出问题的层**混在一起了——这恰好也是本轮四条阻断的共同形状（把两件事写进同一个字段）的一个元级实例。

## 四、本轮四条阻断的共同类根因（写给下一刀）

四条修完之后，回头看它们是同一句话的四个实例：

> **一个由调用方 / 由一次观察 提供的值，被直接当成了「谁有权做什么」或「用户决定了什么」。**

| # | 那个值 | 它被当成了什么 | 收口后的唯一判据 |
|---|---|---|---|
| 4 | `params.projectId`（裸 bearer 提供） | 「我有权改这个项目的画布」 | `leasedProject` + dispatcher 路由闭包测试 |
| 5 | 散着传的 `authType/headerName/scheme` | 「这把 key 该怎么放」（少传一个也合法） | `VendorAuthSpec` 值对象 + `catalog/vendorAuthSpec` |
| 6 | 供应商 `/models` 的一次返回 | 「用户不想用这个模型了」 | `modelListReconciliation` 返回类型里没有 `enabled` |
| 7 | `params.trustLevel`（调用方自报） | 「用户授权了全自动」 | `isTrustDowngrade` + 一次真人证据 |

四条的修法也同构：**把「谁说了算」做成类型或单一 owner，让说不清的那条路在编译期或门岗期红，
而不是在用户面前红。** 这与 `2026-09-11-legacy-spend-door` 的 `class_root` 逐字相同——
那份合同已经在付费轴上说过一次，本轮证明它在**权限轴、鉴权轴、归属轴、审批轴**上各还有一份。

**给编排层的一条**：这四条能被找出来，靠的是两轮**用不同尺子**的横扫（按意图 / 按入口），
而不是任何一份合同的 `same_class_scan`。52 份合同里有 13 份把 `class_root` 写成通用类却只扫 ≤2 扇门
（`sweep-one` §4.7 的 C6）。合同里的 `same_class_scan` 今天是**人手写的一句话**，没有人核它跑没跑过。
这是下一个值得机器化的地方，优先级高于再补一条门岗。
