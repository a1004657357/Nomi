# 结构评审：`src/workbench` 7 天 20 份合同，是同一件事的三个长相

> 触发：`check:symptom-cluster` 报 `src/workbench` 在 2026-09-12 到 2026-09-18 的 7 天里
> 已有 20 份根因合同。门岗的原话是「**第三份合同是『这一层的结构不对』最便宜的证据，不是再修一次的理由**」。
> 这份评审就是它要的那个东西。
>
> **做法**：把 20 份的 `class_root`（合同里「这一类的根」那一栏）全读了，按形状归类；
> 数字都是从合同 JSON 里机器取的。**没做的**：没有逐份复核修复是否真落地，
> 也没有重跑那 20 份的回归测试——本文只判结构，不判交付。

## 1. 数字

| | |
|---|---|
| 合同数 / 天数 | **20 / 7**（2026-09-12 ~ 2026-09-18） |
| `recurrence` 判定 | **20 份全是 `recurring`**，7 天里**没有一份**被判成 `one_off` |
| `invariant_owner_layer` 指向 `electron/` 的 | **8 / 20**——scope 写的是 `src/workbench`，不变量却住在主进程 |
| 门表规模 | 0 ~ 398 扇，中位 16；4 份是 0 扇（都在 09-12/09-13，门表要求的阈值日期之前） |

**「20 份全是 recurring」本身就是结论的一半**：写合同的人（多是不同的会话/工人）各自独立判断，
**没有一个人认为自己修的是一次性问题**。

## 2. 三个长相

### A · 一份语义没有主人 ⇒ 每个消费点各自重答一次（9 份）

| 合同 | 那份没主人的语义 |
|---|---|
| `2026-09-12-model-availability-single-owner` | 「这个模型现在能不能用」——每个新界面各自拼一次「启用+发布+钥匙」的合取 |
| `2026-09-12-storyboard-plan-defaults-passthrough` | 只导出给界面看的 getter，没导出给请求体用的 resolver，发送端各自铺一遍 |
| `2026-09-14-media-import-single-owner` | 「收什么类型/收多大」散在六处各自 hardcode（30MB/600MB/200MB/80MB/64MB） |
| `2026-09-14-resident-generation-adapter-install` | 「常驻生成面装没装」有三份 nullable 影子 |
| `2026-09-15-shot-seconds-precision` | 「镜头时间精确到几位」每处各自发明（0.01 / 两位 / 一位） |
| `2026-09-17-background-run-project-identity` | run 的项目身份不是 run 的属性，每一步都现问「现在开着哪个项目」 |
| `2026-09-17-interactive-import-project-context` | 项目 IO 权限谁想起来谁自取，而不是入口处由主人签发一次 |
| `2026-09-18-storyboard-external-reference-waiting` | 「这张锚要不要参考卡」materialize 与行状态层各写一份判据 |
| `2026-09-14-settings-allowlist-default-deny` | 「允许什么」有**两个** owner，而第二份的空值语义与用户心智相反 |

### B · 两种不同的现实共用一个表示，读者分不开（10 份）

这一类的形状极其统一：**「没有」和「我没办到」长得一模一样**。

| 合同 | 被挤在一起的两种现实 |
|---|---|
| `2026-09-12-announced-card-never-rendered` | 「没有要确认的东西」vs「我没能把它变成一张卡」——共用空数组/undefined，六处各自 `catch { return [] }` |
| `2026-09-13-spend-surface-capability-guard` | 能力不存在 vs 能力调用失败 |
| `2026-09-13-spend-surface-unavailable-error-boundary` | 缺失函数 vs 带稳定错误码的拒绝 |
| `2026-09-14-agent-panel-action-receipts` | 「成功了」vs「什么都没发生」 |
| `2026-09-14-import-borrows-generation-waiting-surface` | 非生成的忙只能借生成的 status 词表，借了就继承整套生成语义 |
| `2026-09-17-import-progress-finishing-phase` | 一个标量（拷贝比例）代表三阶段，没有分母的两段变成**不可见**而不只是未度量 |
| `2026-09-17-session-revocation-outcomes` | 「撤权了」vs「证明没有副作用」 |
| `2026-09-17-project-artifact-storage-and-projection` | 存储 / 放置 / 传输投影三种职责揉在一起 |
| `2026-09-17-surface-handler-error-protocol` | 跨上下文回调返回任意值+抛异常，而不是可序列化的可判别联合 |
| `2026-09-17-document-capability-owner-project-session` | owner 是视图组件而不是已经持有数据的项目会话，下游只能猜视图挂没挂 |

### C · 主人在，但它的实现编译器和测试都看不见（1 份）

`2026-09-15-generation-shell-bottom-band`：外壳的容器关系是不变量，
**唯一实现是一串 Tailwind 类名**——改错既不影响编译也不影响任何既有测试，
于是代码和它自己的走查注释当场对不上，**漂了 5 天没人发现**。

## 3. 判断

**A 和 B 不是两个问题，是同一个问题的两面。**

- A = 没人**回答**这个语义 → 每个读者各自重答
- B = 没人**定义这个语义的边界** → 两种现实挤进一个表示

统一说法：**一个语义没有一个说得出名字的主人时，它就会被重新发明——
要么被重新计算（A），要么被重新解释（B）。**
两种都不会报错，因为「重新发明」在类型上永远合法。

**这不是 `src/workbench` 的问题。** 同一天对 `electron/` 那一层做的评审
（`docs/audit/2026-09-18-electron-unowned-state-structural-review.md`，41 份合同）
得到的是**同一个形状**。再叠上本文的「8/20 的不变量主人其实住在 `electron/`」——
`src/workbench` 这一簇是那同一件事在渲染层的**显形面**，不是一个独立的层级问题。

所以：**不要为 `src/workbench` 单独设计解法。**

### 「分镜表与画布两套账本」在这张图上的位置

这一簇里最被人看见的那条是分镜表——用户把剧本给 Agent，23 轮里画布落了 14 次，
**分镜表仍然 0/23 可见**。它正在被 `fix/storyboard-single-ledger-20260918` 那条 lane 修。

**它是形状 A 的一个实例，不是这 20 份的根。** 对应的合同
`2026-09-18-storyboard-external-reference-waiting` 的 class_root 写得很清楚：
同一个问题「这张锚要不要参考卡」，materialize 层与行状态层**各写了一份判据**，
判据不同源，同一张锚必然在两层得出相反结论——这就是「一份语义没有主人 ⇒ 各自重答」。
「两套账本」是这句话在分镜这条旅程上的具体长相。

**为什么不能把它写成这一簇的根因**：它解释不了另外 19 份。
「这个模型现在能不能用」每个界面各自拼一次、「收多大文件」散在六处各自写死、
「成功了」和「什么都没发生」共用一个表示——这些和分镜表没有关系，
但它们和分镜表**是同一个形状**。把一份的答案写成二十份的根，下一个读者会照着它去找账本，
而真正该问的是「这份语义归谁」。

两件事都要做，但它们是两层：那条 lane 修的是这一个实例，本文第 4 节的建议修的是形状。

## 4. 建议（按性价比，都不改产品行为）

1. **合同模板加一问：「这份状态出生时有主人吗？」**
   20 份里没有一份在事前被这个问题拦住过——因为没人问过。这是最便宜的一刀。
   （这一条与 electron 评审的建议是同一条，合并做。）

2. **B 类是可机器化的，A 类不是。**
   B 的判据具体得能写成门岗：**跨上下文的回调/适配器不许用 `T | undefined` 同时表达
   「没有」和「失败」，必须返回可判别联合**。`surface-handler-error-protocol` 已经按这个修了，
   把它的形状提成规则即可。A 类要靠人判断「这份语义该归谁」，做不成门岗——
   它的防线是 `check:boundary-owners`（已上线）+ 上面第 1 条。

3. **C 类只有 1 份，但它暴露的是一条真空白**：
   不变量的唯一实现不许是「类名字符串」这种编译器和测试都看不见的东西。
   要么有断言，要么有一个能被 import 的 owner 模块。
   量太小，不值得现在做门岗，**但下次再出第二份就该做**。

## 5. 未证实 / 本文没做

- 没有逐份复核这 20 个修复是否真的落地生效——本文只读合同的 `class_root`，不读实现。
- 「8/20 的不变量住主进程」是从 `invariant_owner_layer.layer` 的字符串前缀数出来的，
  没有逐份核实那个层是不是**真的**该负责。
- 第 2 条建议里「B 类可以做成门岗」是设计推断，**没写原型**，不知道误报率。
- 20 份里有 4 份没有门表（09-12/09-13，阈值之前），它们的「同类入口扫全了吗」**无从复核**。
