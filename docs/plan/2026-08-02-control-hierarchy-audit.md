# 全 App 控件层级梳理（2026-08-02）

> 起因：用户说「整个页面上的按钮太多、太杂」。
> 做法：10 路并行把**每一个用户可见控件**逐个登记（含右键菜单、hover 才出的、快捷键、拖拽手势），再找根因、定法、排落点。
> 范围：全部 10 个界面，252 个 tsx，2342 条 i18n 可见文案 key。

---

## 0. 一句话结论

**不是「按钮多」，是「没有一条法管按钮住哪」。** 设计系统管了「长什么样」（token/组件/图标/视觉 pattern，848 行），没有一条规则管「这个控件该常驻、该 hover 才出、还是该收进菜单」。于是十个界面各自发明了十套摆法——画布左缘 8 个平铺竖条、剪辑页一条 toolbar 横铺 15 个跨 4 类心智、3D 四面包围、节点四面包围+浮条+底栏。

不定这条法，这次收拾干净，下个功能进来照样长回去。

## 2. 三条根因（都已实查，不是推测）

### 根因 1：设计系统只管「长什么样」，没管「住哪一层」

`docs/design/nomi-design-system.md` 848 行实读：token 全表、组件库、图标登记、视觉 pattern、反例——**唯独没有一条判定「这个控件该常驻 / 该 hover 才出 / 该收进菜单」**。

后果就是十个界面十套摆法：

| 界面 | 自创的摆法 |
|---|---|
| 画布 | 左缘 8 个平铺竖条 + 左下 5 件混装 + 选中浮条 |
| 剪辑 | 一条 toolbar 横铺 15 个，跨 4 类心智，靠 flex-wrap 换行硬扛 |
| 3D | 四面包围（顶/左/右/底）+ 5 类画布浮层 |
| 节点 | 四面包围 + hover 浮条 + 底栏长条，两组心智同时在场 |
| 顶栏 | 右簇 7 个平铺，无分组无分隔 |

**这是根因。** 不修它，这轮收拾干净，下个功能进来照样长回去。

## 3. 定法：Nomi 控件分层法

### 3.1 一个判定问题

> **「用户在这个面上，10 次里有几次会用它？」**

| 层 | 频次 | 住哪 | 预算 |
|---|---|---|---|
| **L1 主干** | ≥7/10 | **常驻**，视觉最重 | **每个面 ≤5 个** |
| **L2 情境** | 3–7/10 | **选中/hover 才出**，贴目标就近浮现 | 不限，但不许挤进常驻条 |
| **L3 收纳** | 1–3/10 | **一次点击可达的二级**：▾ 菜单 / 参数面板 / 抽屉 | 不限 |
| **L4 溢出** | <1/10 | **⋯ 菜单 / 设置 / 仅快捷键** | 不限 |
| **L0 删** | 0 | 死码、占位、重复入口的第 2..N 个 | — |

### 3.2 三条硬规则

1. **一功能一个家**——同一动作只保留 **1 个规范入口**，其余全删。快捷键和手势**不算入口**，算加速器（可以多，因为不占视觉预算）。
2. **常驻位有预算**——每个面 L1 ≤ 5。要加第 6 个，必须先降级一个。
3. **情境控件不许挤常驻条**——选中才出的东西不能塞进常驻 toolbar（会布局抖动，剪辑页时间轴头部现在就这样）。

### 3.3 这条法进哪

写进 `docs/design/nomi-design-system.md` 新增一节「§4.0 控件该住哪一层」，并进 `CLAUDE.md` 三闸①（动手写码前：用户可见改动先过分层法）。**这是治本的那一步**——不进设计系统，下次照样长回来。

### 5.0 v1 错在哪（记下来，防再犯）

1. **把「常驻 ≤5」当硬指标去凑数**，为了达标连中频控件也收了（抠图 / 优化 / ×N）。→ 「≤5」从此只当**观察指标**，且按**功能簇**算（播放/上帧/下帧/时间/音量 = 1 簇，不是 5 个）。
2. **把已经是二级的东西又包一层，变成三级**：切图▾ / 变换▾ 本来一次点击可达，v1 塞进「编辑▾」→ 要点两次。**为了少一个按钮让用户多点一次，是净负收益。**

### 5.0.1 v2 的顺序：先分组 → 再去重 → 再归位 → 最后才收纳

| 手法 | 定义 | 可达性代价 |
|---|---|---|
| **分组** | 控件一个不少，只是有了边界和名字 | 0 |
| **去重** | 同功能的多个入口收成一个 | 0（减的是真冗余）|
| **归位** | 放错地方的搬回它该在的地方 | 0 |
| **就近** | 情境控件搬到它作用的对象旁边 | 0（且不再让常驻条抖动）|
| **收纳** | 只有真长尾才进 ▾ | +1 次点击 |

**「杂」的主因是没秩序，不是数量。** v2 全 App 真正被「收起来」的只剩一处：3D 的约 40 个逐骨骼姿势滑杆。

### 5.0.3 v2 在画布节点这一面错的两处（用户 2026-08-02 当场指出）

**① 把动作往画面上放，方向反了。**
卡片右上那两颗（放大 · 生成记录）走的是 `bg-nomi-paper/[0.82] backdrop-blur`，**半透明常驻压在图上**——不是 hover 才出（真机 `02-canvas-full.png` 里未选中的节点也带着）。v2 还想再往那儿塞一个「下载」= 3 颗遮挡。

→ 顺带补一条零成本加速器：**双击画面 = 放大**（现在没有，很多人会下意识双击；手势不占视觉预算）。

**② 把模型埋了，还推翻了拍过的板。**
`InlineParameterBar` 源码注释写得很清楚：「section="parameters"：底栏 = 模型芯片 + 变体 + 摘要 pill（当前参数一句话）。**2026-07-17 用户拍板**（样张 `node-param-panel.html`），替代旧「前 2 内联 + 更多弹层」」；`NodeParameterControls.tsx:645` 另有「变体（型号）已挪到底栏 InlineParameterBar 的小下拉（**用户拍板：和模型并排在最下面**）」。
也就是说**底栏已经是「合并过一轮、且拍过板」的形态，模型本来就有独立芯片**。v2 想把「模型 + 变体 + 参数」三颗再合成一句话 = 既推翻拍板，又把用户最看重的模型埋进摘要里。

- 三张主卡、最近项目、搜索、筛选页签**全部原样不动**。

**③ 画布节点** — 画面遮挡 2 → 0；浮条分 4 组；**底栏原样不动**
- <span>去重</span>**卡片角清空**：放大 · 下载 · 生成记录全部归到 hover 浮条。全 App **下载 5 → 1、放大 4 → 1**，两套大图实现（`NodeImageLightbox` / `NodeMediaPreviewDialog`）合并成一套。

**④ 剪辑页** — 控制条 **15 件一件没少**，套进 4 个有名字的组
- <span>分组</span>「播放器组（无标签，形态自明）｜**整片**（画幅）｜**这一段 · 镜 N**（显示 · 取景缩放 · 重置）｜叠加（文字）」+ 导出。

### 5.2 「≤5」按功能簇算，不按按钮个数算

播放/上帧/下帧/时间/音量是一个「播放器簇」，算 1 不算 5。否则规则会机械到反噬体验。

### 6.1 对抗复核（2026-08-04）：改动都真在，但我的四句描述不准

用户问「我怎么没看到设置那些东西」→ 查实是他跑的 `/Applications/Nomi.app` 是 **v0.17.1（7-26 构建）**，
主工作树也落后 origin/main 173 个 commit。**不是改动没落地。**

顺手对 U1–U4 做了一轮对抗复核（每个单元一个取证 agent + 一个专门找反例的复核 agent）。
结论：**5 个单元的代码全部 present、用户路径全部走得通，没有一个是空的**。
但复核抓到**四句我写得不准的描述**——记下来，因为「描述不准」正是这轮根因的同一类毛病：

1. **「hover 浮条」是错的 → 实为「选中才出」。** 门是 `selected && !isMultiSelectActive && !readOnly`，
   光把鼠标移上去不出现，必须单击选中节点。已改正三处代码注释（这种注释会让下一个人按错的前提判断）。
2. **`ToolbarProvenanceButton` 是四处复用，不是三处。** 图片与图编辑是**同一条**浮条
   （NodeImageEditToolbar），另有视频、全景（BaseGenerationNode）、其余结果（NodeResultDownloadButton）。
3. **U1「这些点了没反应的入口从界面上消失了」被我夸大。** 6 项里 5 项用户**从来就够不到**
   （文件浏览器链的 setter 永不触发 / 两个 library modal 全仓零 dispatch / ProvenancePanel 的
   `onRegenerate` 恒空按钮从不渲染 / ToastHost 是 `return null` 空壳 / TrajectoryRendererMenus 零引用），
   删掉零可见差异。**真在屏上的只有运镜「叠一层·敬请期待」那颗禁用占位。**
   准确说法是：删的绝大多数是用户看不见的死码，可见收益仅此一颗。
   另：提示词库/技能库 modal 的删除其实在 `feeb575b`，不在 `5b98b533`。
4. **U4a「4 个有名字的组」不准。** 传输组是**有意不加组名**的（形态自明），实为「3 个带名 + 1 个自明无名」。

**复核提的一条被实测否掉了**（差点去修不存在的 bug）：复核担心「disabled 按钮不触发 hover，
所以 `<span title>` 里的禁用原因够不着」。在我们自己的 Electron 31 / Chromium 126 里实测：
外层 span 照样收到 `mouseover`（命中元素是禁用按钮本身，事件冒泡上去），`display: contents` 也不影响。
**禁用原因看得到，不用改。**
