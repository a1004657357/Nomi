# 切点超上限：不再按时间砍掉后半条片子

> 状态：🚧 进行中（PR #839）· 2026-09-22 · 分支 `fix/shot-cut-truncation-20260922`
> 根因合同：`docs/fixes/2026-09-22-shot-cut-truncation.root-cause.json`

## 0. 一句话

拆一条快剪片子，拿到的分镜表**只拆了前 15%**，而表看起来是完整的、没有任何提示——因为上限是按**时间顺序**取前 120 刀砍的。改成按**分数**抬阈值压，表仍然只有 120 行，但整条片子都在表里。

## 1. 用户那一刻卡在哪

用户把一条 6 分钟的快剪片子拖进来点「拆解」。等了几分钟、花了 120 次读图的钱，拿到一张 121 行的表。

前 120 行密密麻麻，全部落在**第 0 到 55 秒**之间。第 121 行写着 `55.4s – 361.1s`——一个 **305 秒的「镜头」**，它的画面描述是从这 305 秒里抽的 3 帧凑出来的，读起来像胡说。

他不会觉得这是 bug。行号是连着的，时间是接得上的，最后一行的结尾正好是片长。**它看着就是「这条片子就这样」。** 于是他要么以为自己的片子有问题，要么以为 Nomi 的拆解就这个水平。

## 2. 上限本身不是 bug——先搞清它当初在防什么

`MAX_CUTS = 120` 是 2026-08-02 的 commit `03bc89d30`（「按镜头拆」面板）引入的。那个 commit 的原话：

> 切点超过 120 个（快剪 MV）截断并**明着说**，不假装「就这么多」。

代码注释也写着「全铺出来既慢又没法选」。所以它当初防的是**那个预览面板的 UI**：一张 8 列的联系表拼图 + 一个要人逐个勾选的网格，400 多格既拼不出也选不动。

**它不是花钱的闸。** 花钱的闸在 `electron/video/deconstructVideo.ts:398` 的 `authorizeSpend(plan)`——开跑前把「拆几镜、哪个模型、一共几次调用」摆给用户确认，一颗令牌覆盖全批。这一点很重要：它意味着**放开条数不会让谁在不知情的情况下花钱**，报价卡上的数字会如实变大，用户可以不批。

而「按镜头拆」那条路（面板）是**纯本地、零成本**的——上限在那里纯粹是 UI 取舍。

三件事因此对上了：

| | 按镜头拆（2026-08-02） | 视频拆解（2026-09-01，晚一个月） |
|---|---|---|
| 上限防什么 | 联系表拼图 + 勾选网格（本地、零成本） | 顺带限制了付费读图次数（但真闸是 authorizeSpend） |
| 有没有说 | **有**，`NodeShotCutPanel.tsx:228` 一行警告 | **没有**，`detected.truncated` 被整个丢掉 |

拆解那条路是一个月后复用 `detectShotCuts` 的，它只取了 `cuts`，没接 `truncated`。**同一个上限，在一条路上是「说清楚的取舍」，在另一条路上是「静默截断」。**

## 3. 类根因

> 「这批结果给全了没有」这份状态**没有跨进程的 owner**：它是生产者本地的一个可选布尔，读侧可以整个不读，而编译器不吭声。

这不是一次手滑。只要信号是可选的，下一个接 `detectShotCuts` 的读侧（MCP 工具、Agent 拆解、批量拆解）就会以**完全相同的方式**再丢一次。

同一条链上还有第二个同形状的：渲染层 `filterShotCuts` 自己长了一份 0.2 秒的余震合并，**引擎侧一份都没有**——于是同一条视频，面板里看到的刀数和拆解表里的行数不一样，而且拆解那边多出来的每一刀都是一次多花的读图钱。

### 还有一刀砍错了地方

截断发生在**用户灵敏度过滤之前**：

```
detectShotCuts:  parse(447 刀) → slice(0,120)  ← 砍在这里
deconstructVideo:              → filter(score >= payload.threshold)  ← 用户的滑杆在这里
```

所以用户把滑杆拉到**任何**位置，都换不回第 55 秒之后的内容。面板那条路同理。这是「表不完整」之外，更隐蔽的第二重损失。

## 先查别人（§4）：镜头数过多时大家怎么办

全部本次实读一手来源（不是凭记忆）：

| 产品 | 有没有条数上限 | 「太碎」的答案是什么 | 出处 |
|---|---|---|---|
| **LosslessCut** | **没有**。`detectSceneChanges` 逐条 `onSegmentDetected` 全部上报，无 slice / 无 limit | 用户调 `minChange` 阈值 | [`src/main/ffmpeg.ts`](https://raw.githubusercontent.com/mifi/lossless-cut/master/src/main/ffmpeg.ts)（2026-09-22 实读） |
| **Kdenlive** | **没有** | 两个控制：**阈值**（百分比，官方推荐 15–25%）+ **最小间隔** `minInterval`（`if (m_minInterval > 0 && pos - lastCut < m_minInterval) continue;`） | [`src/jobs/scenesplittask.cpp`](https://raw.githubusercontent.com/KDE/kdenlive/master/src/jobs/scenesplittask.cpp)（2026-09-22 实读） |
| **PySceneDetect** | **没有** | `min_scene_len`：「Once a cut is detected, this much time must pass before a new one can be added」+ `filter_mode` 合并 | [detectors API 文档](https://www.scenedetect.com/docs/latest/api/detectors.html)（2026-09-22 实读） |
| **DaVinci Resolve** | 没有 | 置信度曲线图 + 可拖的阈值线 + 人工确认后才入库 | 二手（elements.tv 评测，见 `docs/evidence/2026-09-22-shot-cut-truncation/shot-boundary-research.md` §4；官方手册镜像 404） |

**一条结论**：没有任何一个同类产品用「取前 N」。所有人的答案都是**阈值**或**最短镜长**——两者都保住全片覆盖。我们那一刀是这一族里的孤例。

（LosslessCut 与 Kdenlive 用的 filtergraph 和我们一字不差：`select='gt(scene,X)'`。所以差的不是算法，是超限策略。）

## 5. 三种压法的实测对比

**素材**：三条真实片子，历史对比使用本机 PATH ffmpeg，生产同款 filtergraph `select='gt(scene,0.1)',metadata=print`，零模型花费。随附二进制现场 `-version` 为 **ffmpeg 4.4**；此表历史数字不冒充随附版本的重新测量。

> **证据边界（2026-09-22 归档时补记）**：本节与 §6 两张表的**计算脚本**（原 `scratchpad/trunc/compare.mjs`、`sweep.mjs`、`compare.json`）**原始数据未能归档，数字为当时记录**，本次没有重新跑过。
> 两张表的**输入**在：`docs/evidence/2026-09-22-shot-cut-truncation/sbd/results/ffmpeg-select-F{1,2,3}.txt`（逐帧分数，77 / 51 / 447 行，与下表「ffmpeg@0.1 报几刀」一行对得上）与 `…/cuts.json`（真值；F3 的 TransNetV2 p>0.5 = 65）。
> 另：下表 F1 / F2 的「人工 52 刀 / 45 刀」那份标注没有落进任何文件，**同样未归档**。

| | F1 `demo-video.mp4` | F2 `demo-en.mp4` | F3 快剪电影开场 |
|---|---|---|---|
| 片长 / 帧率 | 202.9s @30 | 287.4s @23.976 | 361.1s @29.97 |
| ffmpeg@0.1 报几刀 | 77 | 51 | **447** |
| 真值 | 人工 52 刀 | 人工 45 刀 | TransNetV2 p>0.5 = 65 刀 |
| 超上限？ | 否 | 否 | **是** |

只有 F3 触发上限。四种压法（都先做 ≤2 帧去重，399 刀）：

| 策略 | 采用 | 覆盖到 | 覆盖率 | 最长一镜 | 精确率 | 召回 | F1 |
|---|---|---|---|---|---|---|---|
| **A 取前 N（真实 main）**² | 120 | **52.7s** | **14.6%** | **308.4s** | 0.242 | .509 | .328 |
| B 分数 Top-N | 120 | 348.1s | 96.4% | 40.3s | 0.492 | 0.908 | **0.638** |
| **C 抬阈值到 0.2022**¹ | 120 | 348.1s | 96.4% | 40.3s | 0.492 | 0.908 | **0.638** |
| D 并短镜（Kdenlive 那套） | 120 | 348.1s | 96.4% | 40.3s | 0.425 | 0.785 | 0.551 |
| （参考）不压 | 399 | 348.1s | 96.4% | 40.3s | 0.163 | 1.000 | 0.280 |

² 口径更正（验收指出）：真实 `origin/main` 是对**未去重的 447 刀**做 `slice(0,120)`，覆盖只到 52.686s / 14.6%、巨镜 308.4s。
本表此前那一行按**去重后 399 刀**取前 120 算（55.4s / 15.3% / 305.7s）——**真实 main 比表里还差一点**，结论方向不变。

¹ 生产实现用的是**严格**大于（`score > appliedThreshold`，与 ffmpeg 的 `gt(scene,T)` 对齐），实际阈值 `0.202157`、采用 120 刀、覆盖到 348.081s。对比脚本当时用的是 `>=`（0.205537），两者采用条数与结果集相同，只差阈值的表示。

**A 是灾难性的**：召回只有 0.446，因为它压根没看后面 85% 的片子。

**B 和 C 结果完全相同**——这不是巧合：「留下分数最高的 N 个」和「把阈值抬到恰好剩 N 个」是同一个集合（差别只在并列分数的处理）。顺带一个发现：**「抬阈值重检」不需要重跑 ffmpeg**——0.1 的全集已经带着分数，高阈值只是它的子集，再解一遍码纯属浪费。

### 选 C，有三个独立理由

1. **准确率并列第一**（与 B 相同，F1 0.638 vs A 的 0.314）。
2. **它是一个用户能看懂、能动的数**。「灵敏度自动提到了 0.21，想更细就往左拉」——直接接上面板里**已经存在**的灵敏度滑杆。B 的「前 120 高分」不对应滑杆任何一个位置，说不清也调不动。
~~3. 只有它能让联系表保持一趟 ffmpeg 拼出来。~~ **作废**：这条理由建立在「让 ffmpeg 按阈值再筛一遍
就能复现同一批帧」这个前提上，而 §10.5 证明**前提本身是错的**。改成按 pts 点名后，任何子集都能一趟拼出来，
B/D 在这一项上与 C 同等。**去掉它之后选 C 仍然成立**，靠剩下两条（准确率并列第一 + 它是用户能直接在滑杆上调的数）。

D（并短镜）在「时间上更均匀」这项上最好，但它用召回换（F1 .551 vs .638）。
**它更适合作为一个用户可见的「最短镜长」控件**（Kdenlive 正是这么给的），而不是一个自动兜底——见 §8。

**去掉那条作废理由后，选 C 仍然成立**，靠的是剩下两条：准确率并列第一，且它是一个用户看得懂、
能直接在现有灵敏度滑杆上调的数。

## 6. ≤2 帧去重

ffmpeg 常把一个硬切报在相邻两帧上。窗口扫描（三条素材，容差 ±3 帧）——**扫描脚本原始数据未能归档，下表数字为当时记录**，输入见 §5 的证据边界一段；`extra-experiments.json` 里留有 `F1_ffmpeg0.1_dedup` / `F2_ffmpeg0.1_dedup` 等几条的 n / P / R / F1：

| 窗口 | F1 精确/召回/F1 | F2 精确/召回/F1 | F3 刀数 → F1 |
|---|---|---|---|
| 无去重 | .571 / **.846** / .682 | .882 / **1.000** / .938 | 447 → .254 |
| **2 帧** | .603 / **.846** / .704 | .978 / **1.000** / **.989** | 399 → .280 |
| 3 帧 | .611 / .846 / .710 | .978 / 1.000 / .989 | 378 → .289（召回掉到 .985）|
| 5 帧 | .652 / .827 ⚠️ / .729 | .978 / 1.000 / .989 | 325 → .328（召回 .985）|
| 0.2s（渲染层现役）| .689 / .808 ⚠️ / .743 | .978 / 1.000 / .989 | 199 → .477（召回 .969）|

**2 帧是三条素材上召回一点不掉的最大窗口**——它只拿掉重复，不删真刀。再往上 F1 更好看，但那是**拿召回换的**：0.2 秒在 F1 素材上吃掉了 2 个真实快剪。那是产品取舍（「最短镜长」），不是去重，所以不能偷偷做。

顺带：去重直接省钱。拆解那条路每一刀就是一镜、每一镜一次付费读图，重复刀 = 重复账单。三条素材分别省下 **5.2% / 9.8% / 10.7%** 的行。

## 7. scdet 的处置

**本次不做。** §5 选定的 C 只需要「每个切点的分数」，而现役 `select + metadata=print` 已经给了。`scdet` 的价值是拿到**全帧**分数曲线（用于 Resolve 那种可视化曲线、或自适应阈值），那是另一件事，留给做那条曲线的时候一起做。实测两者算法相同、耗时持平（见 `docs/evidence/2026-09-22-shot-cut-truncation/sbd/REPORT.md` §2.2）。

## 8. 默认阈值 0.1：只给数据，不改

**没有改，也不建议在本次改。** 数据：

- 0.1 在 F2 上召回 1.000、精确率 0.978（去重后）——**这条片子上它是对的**。
- 0.1 在 F3 快剪片上精确率只有 0.163：447 刀 vs 真值 65 刀，大量运镜/闪光被当成切点。
- 但 0.1 是**检测下限**，不是展示值：面板的滑杆默认 0.3，且 `pickDefaultSensitivity` 会按这条片子自己的分数分布回退。真正决定用户看到多少的是滑杆，不是这个下限。

**建议**：`SHOT_CUT_DETECT_THRESHOLD` 保持 0.1（降低它会漏掉弱切点的片子，那类片子最强的刀只有 0.161）。该调的是**拆解那条路的默认灵敏度**——它现在默认不过滤（`payload.threshold` 缺省就是全集），而面板默认 0.3。两条路默认值不一致，本身就是一个待拍板的产品问题。**这属于产品行为改动，等用户拍板。**

## 9. 用户可见那一层：出选项，不实现

数据字段已经备好（`source.cutCoverage` 带 `detectedCuts / keptCuts / appliedThreshold / capped / coveredSeconds / durationSeconds`）。分镜表节点上**还没有**任何提示。读过真实外壳（`ShotTableNode.tsx` / `ShotTableGrid.tsx`）后给三个选项：

### 卡点四问

| 问 | 今天的答案 |
|---|---|
| 用户怎么知道这张表不完整？ | **不知道**。表看着是完整的 |
| 动手前知不知道重拆要花多少？ | 知道——`authorizeSpend` 报价卡会摆出「拆几镜、几次调用」 |
| 他看到什么？ | 121 行，最后一行是个 305 秒的「镜头」 |
| 怎么回头？ | 没有入口。滑杆够不到（截断在过滤之前） |

### 三个选项

**选项 1 — 表头一行状态条（最小）**
> ⚠️ 这条片子切点很密（399 个），已按变化强度取了最强的 120 个。整条片子都在表里，但相邻的弱切点被并到了一起。

- 好：一行字，零新控件，和现有 `errorMessage` 那一行同一个位置、同一套样式。
- 差：说了问题没给出路，用户想更细只能重拆而不知道怎么重拆。

**选项 2 — 状态条 + 「拆得更细」按钮（推荐）**
> ⚠️ 切点很密（399 个），已取最强的 120 个 —— 整条片子都在表里。 **[拆得更细…]**

点按钮 → 弹现有的报价卡，把阈值降一档、行数与调用次数如实显示，用户确认才跑。
- 好：D1「effect-first」——直接给他下一步动作，不是让他读一段解释后自己想办法；复用已有的付费确认卡，不新造花钱路径。
- 差：多一个按钮；需要 `deconstruct` 支持带 `threshold` 重跑（payload 已经有这个字段，接线成本低）。

**选项 3 — 行内标记被并掉的镜**
在那些「并掉了弱切点」的行上打一个小角标，悬停说明「这一镜里还有 3 个较弱的画面变化」。
- 好：信息落在**发生的地方**，最诚实。
- 差：要把「哪些刀被并掉了、并进了哪一行」也带到渲染层（今天的 `cutCoverage` 只有汇总数）；角标密集时很吵。与 R2「每条信息问有没有行动价值」冲突。

**推荐选项 2**，理由：选项 1 只说不给路（D4 诚实但不解决摩擦），选项 3 的信息量与它的行动价值不成正比、且要扩数据契约。选项 2 用一行字 + 一个按钮闭合「知道 → 能改」，且复用了已有的报价卡，没有新造花钱路径。

## 10. 范围 / 不动项 / 回滚 / 验收门

### 改了什么
- `electron/video/detectShotCuts.ts`：① 压上限从 `slice(0,MAX_CUTS)`（按时间砍）改为 `capShotCutsByScore`（按分数抬阈值，并列时 `pickEvenlyByTime` 按时间补齐到上限）；② 新增 `dedupeShotCuts`（≤2 帧）；③ 联系表改为 `buildSheetFilter` **按整数 pts 点名选帧**，不再按分数重筛；④ 行数收成唯一算式 `shotSheetRowsFor` 并随结果下发（`sheetRows`）；⑤ `truncated: boolean` → `coverage: ShotCutCoverage`；⑥ 压上限走 `logInfo`（正常事件，不是错误）。
- `electron/shared/canvas/shotTable.ts`：新增 `shotCutCoverageSchema` —— 这份状态的唯一 owner；`source.cutCoverage` 可选（只为读回老表）。
- `electron/video/deconstructVideo.ts`：构造 `cutCoverage`（**必填**），按本层实际采用条数算，不照抄检测层。
- 渲染层：`deconstructionTypes.ts`（新增 `StoredDeconstructionResult`，legacy 读回不再无校验强转）/ `shotTableFacts.ts` / `bridgeMedia.ts` 类型镜像与落盘映射；`shotCutSelection.ts` **删掉**自己那份行数算式；`NodeShotCutPanel.tsx` 改读 `coverage.capped` 与下发的 `sheetRows`；i18n `shotCuts.truncated` → `shotCuts.capped`。

### 不动项
- `MAX_CUTS` 仍然是 120（压的是「一次给多少」，不是「看多长」）。
- `SHOT_CUT_DETECT_THRESHOLD` 仍然是 0.1（§8）。
- `authorizeSpend` 付费闸一字不动。
- 渲染层 `filterShotCuts` 的 0.2 秒余震合并**保留**：它现在跑在已去重的输入上，窗口严格更粗，面板行为不变。它实质上是 Kdenlive 的「最小间隔」，应该收成用户可见控件——属产品取舍，本次不动。
- 分镜表节点 UI 不动（§9 只出选项）。
- `docs/plan/2026-09-06` 提的「表节点 48 行硬上限」**从未实现**，本次也不实现；那个取舍仍然开放，唯一结论是：别把它做成取前 N。

### 回滚
单 commit 回滚即可恢复旧行为。已落盘的表里多出的 `source.cutCoverage` 在旧代码下会被 zod `.strict()` 拒绝——**回滚前须先确认没有用新版拆过表**，或同时回滚 schema。老表（无该字段）在新旧两版下都能读。

## 10.5 返工：第一版被验收打回的两条阻断（2026-09-22）

独立验收拿**真实素材**跑了一遍联系表逐格比对，抓到两条第一版自己引入的阻断。两条是同一个形状，
也正是本文 §3 说的那个类根因的又两个实例：**同一个量在两个系统里各有一份判据，边界上不一致且不报错。**

### 阻断 A：联系表与表行错位（第一版的核心论据在真实素材上是假的）

第一版让联系表用**同一个阈值** `gt(scene,T)` 重筛来「原样复现」那批帧。前提是「JS 的 T 和 ffmpeg 的
scene 会做出同样的判断」——可 JS 手里只有 `lavfi.scene_score` **打印出来的 6 位小数**，
ffmpeg 的 `gt()` 比的是内部全精度 double。分数**恰好等于阈值**的那一帧，JS 按 `>` 排除、ffmpeg 收下。

- 实测：`gt(scene,0.202157)` ffmpeg 实吐 **129** 帧，JS 以为 128。多出来的是 110.81s 那一帧。
- 后果：120 刀里 **21 刀（17.5%）指向错误格子**；末刀真实格号 128，**超出 8×16 的容量，根本不在图里**。
- 概率：阈值**必然**取自某一帧的打印值，所以约**一半**压上限的片子都会中。

**修法：按整数 pts 点名选帧，不再让 ffmpeg 自己筛。**
`select='eq(pts\,A)+eq(pts\,B)+…'` —— JS 那份清单成为唯一真相源，ffmpeg 只负责照单抓帧。
pts 是整数，没有精度可言，于是「第 i 格 = 第 i 刀」**由构造保证**，不再是「两边应该算得一样」。

| 方案 | 逐格比对（16×12 灰度平均绝对差） | 耗时 |
|---|---|---|
| 旧 `gt(scene,T)` 重筛 | 快剪电影开场 **107/120 错**；派生真素材 **90/120 错**（最差 82.8） | — |
| **新 按 pts 点名** | 两条素材均 **0/120 错**（最差 2.4，JPEG 噪声量级） | 2.54s |

**为什么不选「阈值取两档中点」**（验收给的备选 a）：治不了根。两帧的**真值不同但打印值相同**时，
任何阈值都分不开它们，ffmpeg 仍按我们看不见的真值取舍。中点法只是把出错概率调低，
而这一类的定义就是「低概率、不报错、错得很安静」——降低概率恰恰让它更难被发现。
按身份点名是把这条缝**消掉**，不是调窄。

**表达式长度**：一条 `eq(pts\,NNNNNNN)+` 约 16 字节，条数由 `MAX_CUTS`=120 封顶 ⇒ 最长约 2KB。
历史 PATH 版本实测 1994 字节、2.54s；这不是随附版本的耗时证据。随附 ffmpeg 4.4 的执行覆盖由真素材测试提供。长度**不随片长增长**，只随 MAX_CUTS——
抬高 MAX_CUTS 时要重新验（已写进合同的 residual_risks）。

### 阻断 B：联系表格子数是双真相源（第一版新引入的回归）

主进程按 `emittedCount` 算行数，渲染层又按 `max(sheetIndex)+1` 算一遍。两者只在「最后一帧恰好是
被去重并掉的余震」时差 1；而 `background-size` 的高度按行数算，**少一行就把整张联系表竖向压扁**，
所有格子一起错位。实测 575 个模拟片长里 0.4%–2% 会中，**不压上限的普通片子也会中**
（修复前两侧都用 `cuts.length`、恒等，所以这是第一版新引入的）。

**修法：行数只留一个算式** `shotSheetRowsFor(cutCount, columns)`（`detectShotCuts.ts`），
同一个数既喂 `tile=CxR` 也随结果下发（`sheetRows`）。渲染层的 `shotSheetRows` / `shotSheetTileCount`
**同 commit 删除**。另加一条廉价的回归提醒：源码扫描匹配已知的行数/格子数算式；换个变量名或写法即可绕过，不能证明不可能分叉。
真正起作用的是结构：`sheetRows` 只在 `shotSheetRowsFor` 算一次并随结果下发。

### 顺带修掉的两条建议项

- **C 并列分数没有下限**：200 刀分数全同 → 阈值取第 121 名 = 同一个分 → `score > T` 得到 **kept=0**
  → `buildShotBoundaries` 给出一个整片长的镜头，**等于换条路走回这次要修的那个症状**。
  现在并列那一档按**时间均匀**补齐到上限（`pickEvenlyByTime`）。
- **D「必填」有个运行时后门**：`readNodeDeconstruction` 是无校验强转，老节点 meta 里没有
  `cutCoverage`，强转后运行时就是 `undefined`，而类型写着必填——**类型说了谎**，正是这次要消灭的形状。
  改成返回 `StoredDeconstructionResult`（该字段可选）。改完编译器当场抓出 `factBridge.ts` 一处真的 legacy 路。
  **不补默认值**：老数据里没有任何依据能还原它当时是不是被压过上限，编一个 `capped:false` 就是伪造证据。
- **E 面板同屏两个「个数」**（标题「检测到 50 个镜头」/ 横幅「取了其中 120 个」）易混 —— 只记录，
  归 §9 出样张时一起处理，本次不改。

### 这轮的方法论教训

第一版**单测全绿、合成夹具零发现**，而真实素材上 120 刀错了 21 刀。原因很直接：
按实测分布**造**出来的夹具碰不到 JS 与 ffmpeg 之间的精度边界——那条缝只在真 ffmpeg 的真输出里存在。
所以真实素材那一格从「债」升级成**挡合入**，且验收内容必须是「真的拼一次联系表并逐格核对」，
而不只是核对中间量（`kept === filter(score>T)` 这种自洽检查在第一版里是绿的）。
