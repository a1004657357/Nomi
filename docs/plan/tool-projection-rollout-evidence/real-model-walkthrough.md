## 三、「参数一次就对」那个数要这么读

逐轮口径下 after 是 0/13、before 是 9/13，看起来像回归。**它不是**，两个理由都可复核：

- 逐轮口径惩罚「干得多」：一轮里只要有**一次**参数被拒就算不对。after 这 13 轮发了 85 次
  `draft_shots`，before 只发了 31 次——before 的 9 个「一次就对」里有 8 个是**那一轮压根没调** `draft_shots`。
- 按**每次调用**算，两臂一样：before 12/40 次被拒（30%），after 19/85 次（22%）。

而且被拒的**全部**是同一件事，且不在我们这一侧：模型把 `shots` 写成一个 JSON **字符串**，而那个字符串
本身是坏的（实测样例：`"durationSec": '/'4`——引号里混进了垃圾字符）。三轮全量统计：

| 跑次 | `draft_shots` 调用数 | `shots` 给的是数组 | 给的是**坏** JSON 字符串 | 给的是**好** JSON 字符串 |
|---|---|---|---|---|
| 本分支（单独 23 轮） | 117 | 87 | 28（24%） | **0** |
| 本分支（A/B 臂） | 85 | 65 | 19（22%） | **0** |
| origin/main（A/B 臂） | 40 | 28 | 12（30%） | **0** |

「给的是好 JSON 字符串却被拒」三轮加起来 **0 次**——说明 `modelArgumentTolerance({ arrayFields: ["shots"] })`
该捏合的都捏合了，剩下的是模型自己吐坏了，pi 的 ajv 当场 fail-closed。这是对的行为，不是缺陷；
但它每轮要多花一两个来回，是下一刀该盯的**模型侧**问题（换模型/换供应商，或者把 `shots` 拆小）。

   工具结果正文全文就是 `capability_input_invalid`，没有第二行——模型无法自纠。对照同一批轨迹里
   `draft_shots` 被拒时回的是字段名 + 期望 + 收到的参数，模型看完就改对了。已开后台任务。

   连续 19 轮全部超时、零工具调用，汇总打出一个看起来像产品结论的 `4/23`。走查侧已经修（每轮先用
