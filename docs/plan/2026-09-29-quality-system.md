# Nomi 质量体系：从「代码通过」改成「用户做成了事」

> 状态：✅ 用户 2026-09-29 拍板（「按这套体系搭，没验证的功能标实验中」）。本文是之后所有改动、测试、发版的唯一依据；与它冲突的旧做法，以本文为准。
> 起因：2026-09-29 用户实际使用 0.22.1，很快碰到十几个问题；随后又发现几件事：
> - 生成结果只有一条路在上报；
> - Agent 轨迹上报从没接线；
> - 新装机改不了 APIMart 的接口地址；
> - 花钱确认整套按「知道价格」设计，实际却从来不知道价格。
>
> 用户原话：「看着好像有很多功能，但是用起来发现各个地方都不能用。」
> 相关：[`2026-09-26-architecture-single-owner-governance.md`](2026-09-26-architecture-single-owner-governance.md)（#897，结构收敛），[`../audit/2026-09-29-hot-modules-structure-review.md`](../audit/2026-09-29-hot-modules-structure-review.md)（热模块结构评审）。

## 先给判断

已有的规矩和门岗检查的是「代码对不对」，查不到「用户用不用得成」。再加上改得太快（2026-09 一个月落了 600 多份根因合同），问题总要拖到用户手里才暴露。修法不是再加门岗，而是换掉「做完」的定义：**做完 = 用户在真实环境里做成了这件事，而且我们看得到证据。**

## 先查别人

检索记录见 [`../research/2026-09-29-quality-system/prior-art.md`](../research/2026-09-29-quality-system/prior-art.md)。结论：五层里每一层都有成熟做法可抄，不自研一套新理论。自研的只有「把这些接到我们现有的剧本、门岗和反馈接收端上」这一层。

| 问的是什么 | 别人怎么做（出处） | 我们照做还是不同 |
|---|---|---|
| 按「用户要完成的事」定义质量，并给每件事量成功率 | Google SRE 的关键用户旅程（CUJ）与 SLO：https://sre.google/workbook/implementing-slos/ | 照做：功能状态表的每一行就是一条旅程，第 5 层按旅程统计成功率 |
| 可靠性跌破线就停新功能 | Google SRE 错误预算政策：https://sre.google/workbook/error-budget-policy/ | 照做：修完 4 个水下问题前冻结新功能 |
| 先给少数人用，再放开 | Chrome 的 Canary / Dev / Beta / Stable 分渠道发布：https://www.chromium.org/getting-involved/dev-channel/ | 照做：先推预览版渠道，再推正式版 |
| 每个功能的所有状态都要设计出来 | 「UI Stack」：理想、空、出错、部分、加载各态都要设计：https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/ | 照做：状态表每个状态都写用户看到的字和能做的动作 |
| 把状态和允许的转换写死，不可能的状态写不出来 | 状态图（statecharts）：https://statecharts.dev/ | 部分照做：我们已有的阶段时限穷举表（`generationPhaseDeadline.ts`）、`narrate.ts` 的穷举动作表就是这个思路，这次把它扩到每条旅程 |
| 每种错误有固定说法和建议动作 | Stripe 错误码目录：https://docs.stripe.com/error-codes | 照做：错误只从唯一的错误目录取文案和动作，不许各处拼 |
| 先修 bug 再写新代码 | Joel Test 第 5 条：https://www.joelonsoftware.com/2000/08/09/the-joel-test-12-steps-to-better-code/ | 照做：冻结期只修不加 |

## 这几天暴露的失败类别

| 类别 | 实例 | 由哪一层拦 |
|---|---|---|
| 测试绕过真实路径 | 删节点的上报测试直接写仓库，绕过了 IPC 校验；派发闸的单测前提顺序不对 | 第 3 层 |
| 出错不吭声 | 渲染层 `catch {}` 吞掉拒收一个多月；`src/` 有 46 处空 catch | 第 3 层 + 门岗棘轮 |
| 做了一半，没人在现实里核对 | Agent 轨迹从没接线；制作流程不上报生成结果 | 第 2、5 层 |
| 新装机和老装机行为不同 | 认证锁只在新装机挡住改 APIMart 地址 | 第 3、4 层 |
| 悄悄去掉已有能力 | 同上，没有人列出「改地址」这项能力被去掉 | 第 1、4 层 |
| 按不存在的世界设计 | 花钱确认按「知道价格」设计，结果永远是「仍要生成」 | 第 1 层 |
| Agent 说的话和事实不符 | 「已经开始跑」「两镜都在队列中」 | 第 3 层（铁律 4） |
| 同一件事多处在管 | 两台生成发动机；停下的原因被误当成「预算」 | 结构收敛 + 概念主人门岗 |
| 判断过严、归错责任 | 解码校验太严判失败，还劝用户换一家 | 第 3 层（铁律 3、4） |
| 没有上限、没有时限 | Agent token 爆掉；一直停在「正在存」 | 第 3 层（铁律 5、8） |
| 界面噪音 | 没用的角标、提示框伸出屏幕、英文原话 | 第 2、3 层（铁律 7、9） |
| 流程本身出错 | 合并收据只看目录不看文件，在没收据时合了下一个 | 协调会话纪律（见文末） |

## 五层防护

### 第 1 层：动手前——改动说明 + 测试表

每个改动（每个 PR）在写代码前先写两样东西，都放进 PR 正文：

1. **用户能力变化**：新增 / 改变 / 去掉三栏。**去掉或挡住一项已有能力，必须用户点头。**
2. **测试表**：

   | 编号 | 在哪、做什么 | 应该看到什么 | 我们的结果 | 用户的结果 |
   |---|---|---|---|---|

   - 每一行都是用户能照着做的动作，不写代码术语；
   - 新装机、老装机升级分开列；中文、英文界面分开列；
   - 「我们的结果」必须真的逐条跑完，附截图；跑不了的写原因，不许空着冒充通过。

设计时必问一句：**「这个设计的主路径，在今天的现实里走得到吗？」** 例如价格今天不存在，所以任何以价格为主路径的确认设计都不成立。

### 第 2 层：产品地图——功能状态表（活的）

`tests/ux/full-walk/catalog.mjs` 每一行是一条用户旅程，字段包括：
- 状态：用户看到的字、能做的动作、由谁决定（代码里的主人，对上 `docs/engineering/concept-owners.json`）、非终态最长等多久；
- 覆盖它的剧本、核对的铁律、要上报的成功 / 失败事件。

目录自检接进 contracts：主人符号必须真实存在；每行至少一条剧本；每个非终态都有时限；每行都有上报事件，没有就写 `gap`。

第一版 10 条旅程：
- 生成一张图；
- 图转视频；
- 连参考图生成；
- Agent 起草多镜并确认；
- 暂停后继续；
- 删镜头；
- 换模型；
- 给 Agent 传附件；
- 导出成片；
- 打开旧项目。

### 第 3 层：每次改动都跑——真 App 剧本 + 九条铁律

- 真 App（Electron）、真点击，经过真实的 IPC 和真实的校验层；**绕过真实边界的测试不算证据**。
- 默认用本地假供应商，不花钱；网络层拦住所有真实供应商域名，漏出去就判红。
- 每条剧本跑两份资料：全新安装，以及从上一版升级上来的资料。
- 每条剧本都配几种乱用变体：暂停、删除、换模型、撤销、切英文。
- 九条铁律：
  1. 没经用户点头不花钱；
  2. 同一镜头不重复扣钱；
  3. 界面上看到的就是发出去的；
  4. 说的都是真的（Agent 和界面的状态文字与后台一致）；
  5. 不会永远转圈；
  6. 用户没动的东西不会自己动；
  7. 看得见、关得掉（关闭钮在视口内；英文界面没有中文）；
  8. 不白烧 token；
  9. 不显示没用的东西。
- Agent 的测法：
  - 手（工具）按状态表和铁律测；
  - 嘴（它说的话）与真实状态自动比对；
  - 脑（整体能力）按统计评测：同一批任务用真模型跑多次，看工具写对率、任务成功率、token、耗时。
  - 设计上「Agent 只提议，系统来决定」：会花钱、会改界面的事，必须过和人亲手点按钮同样的闸。

### 第 4 层：发版前——四道门 + 版本差异体检

1. **版本差异体检**：把上一版标签到候选版之间所有 PR 的「能力变化 + 测试表」汇成一张版本测试表，对到功能状态表的行。每条改过的旅程，新装机、老装机升级各测一遍。
2. **铁律全绿**：至少铁律 1–4（花钱与说真话）必须全绿。
3. **AI 当创作者**：用最便宜的真模型按剧本跑一遍，先清掉明显问题。
4. **用户亲手测**：用户拿候选版，对着版本测试表逐条测。
5. **先给预览版用户**：没问题再推给所有人。

### 第 5 层：发版后——数据说话

- 反馈雷达（`pnpm run intake:radar`）每次会话开始自动跑：按旅程统计成功率、新反馈、错误突增；拉取失败要明说「没查成」。
- 前提是数据完整：制作流程和 Agent 付费卡的生成结果要在唯一的终态处上报；Agent 轨迹只在用户同意后上报，而且必须经过「帮 Nomi 变好」总开关。
- **结果账**：每件事写一句「做成了是什么样」（必须是现实里看得到的结果）和最后核对时间，看到结果才算做完。
- 发版后 3 天内数据异常，就回滚或热修。

## 功能分级：只有验证过的才算正式功能

- 核心旅程过完第 2–4 层才算「正式」。
- 还没过关的功能标「实验中」；其中会花钱的，默认关闭，由用户自己打开。标签怎么显示、开关放在哪里，先出样张给用户拍板。
- 平台维护状态同理：没在维护的平台如实标出来，不删。

## 节奏

- 修完 4 个水下问题前冻结新功能：①批准与派发 → ②话从状态读出 → ③上限与时限 → ④谁发起的。赚钱的接入单子例外。
- 小批量：一个概念同一时间只归一条线；同时跑的实现 agent 控制在 2–3 个。
- 发版攒一批再发；热修只给「用不了 / 花钱错 / 丢数据」。

## 检查点

两到三周内，0.23 要过完四道门：铁律 1–4 全绿，生成成功率的数据可信，并且大多数生成能成功。做不到的话，就把产品收窄到最小核心（画布生成 + 时间轴导出 + 一家中转），其余先藏起来，稳一个放回一个。

## 协调会话的纪律

- 合并收据以 `.git/nomi-delivery/merged-main/<sha>/ci-evidence.json` 文件为准，并确认核心冒烟是 success；退出码不经管道取。没有收据，不合下一个。
- 汇报时不把「测试绿了」说成「做完了」。
- 新问题先问「删掉什么它就没了」，再考虑加门岗。
