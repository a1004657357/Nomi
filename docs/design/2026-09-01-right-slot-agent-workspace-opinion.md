# 右槽 = Agent 工作区 —— 给 M 线交互 epic 的意见书

日期：2026-09-01 · 状态：📋 意见书（拆解线输入，右槽终局定义权归 M 线交互 epic）
出处：拆解视频 v1（`docs/plan/2026-09-01-video-deconstruction-v1.md`）设计过程中抓出的右槽撞车问题 → 用户 2026-09-01 拍板③合流

## 背景

拆解视频 v1 设计时，用户抓出**右槽撞车**问题：右侧就近停靠位今天住着「生成」AI 栏、M 线后要住完整 Agent 面板，而拆解结果面板也想停这里。这引发了交互形态的**三选一**讨论：

- **① 独立面板 + 互斥**：拆解自成一个右侧面板，与 AI/Agent 栏抢同一个槽、谁被唤起谁进驻、另一个让位。
- **② 全进聊天流**：拆解结果作为一条 Agent 消息塞进会话流，没有独立停靠区。
- **③ 合流**：右槽整体升级成 Agent 工作区，会话流与「需要审阅/操作的工件」分区共存，拆解是工作区里的一张结果卡。

用户 **2026-09-01 拍板 ③合流**。本意见书把③的终局定义与论证固化下来，交给 M 线交互 epic 作为输入。

---

## 提议给 epic 的终局定义

**右槽整体 = Agent 的家**，双区：

- **主体 · 会话流**：指挥 / 追问 / 进度 —— 用户对 Agent 说话、Agent 回话、报进度都在这条流里。
- **固定 · 结果卡区**：需要**审阅 / 操作**的工件停靠在这里，**不随聊天滚走**。拆解分镜表、未来的其它可操作产出，都是这个区里的一张卡。

**核心原则：新功能 = 新卡片，不再新立面板。** 右槽在结构上是**单壳**——任何「需要贴着画布、需要审阅操作」的新能力都进结果卡区加一张卡，而不是在画布右缘再挂一个并排面板。这从根上掐掉「面板增生」。

---

## 七维论证摘要

1. **注意力单点**：用户任一时刻只面对一个右侧上下文。独立并排面板会逼用户在两块面板间分心——既有**切换成本**（在两个面板间来回切焦点），又有**翻找成本**（结果在哪个面板里）。合流后两种成本都消。

2. **结果不被滚走**：结果卡区是**固定**的，不随会话流滚动。这对拆解尤其关键——**「对照修改」是拆解落地后的最高频后续动作**（对着分镜表逐镜改提示词、勾选、落节点），结果一旦被聊天顶走就得反复往回翻。

3. **高密度操作全幅可用**：拆解分镜表是高密度多字段表格（景别/情绪/画面/字幕/对白/图片提示词/运镜提示词 + 逐镜勾选）。它占住结果卡区就能用满槽宽做全幅布局，而不是挤在一条聊天气泡里。

4. **指挥型 / 亲手型同壳两用**：合流后一个壳同时服务两种用法——**指挥型**用户走会话流（「帮我把这条拆了」）、**亲手型**用户直接在结果卡区勾选操作。这对齐**已批准的权限档位**：全自动档只走会话 + 画布（Agent 自己拆自己落）、确认档 / 手动档用结果卡区（用户看着卡、逐项确认或亲手勾）。不为两种用法造两套 UI（那是并行版，违反 P4 通用第一）。

5. **空间记忆可回**：工件有**双锚点**——画布上的源节点、结果卡区里的卡。用户切走再回来，从节点或从卡区任一处都能找回同一个工件，符合空间记忆。

6. **实施不等 epic**：**结果卡语法先行**。拆解 v1 现在就按「结果卡」契约实施，epic 那层双区外壳落地时，卡按契约平移进结果卡区即可，不返工。

7. **防面板增生**：结构上**单壳**——右缘只有一个 Agent 工作区，新能力加卡不加面板。这治本地掐掉「三个面板抢右缘互相挤、布局抖」的老坑（`nomi-design-system.md` §1.5「情境控件不许挤常驻条」栽过）。

## 结果卡契约（epic 可直接采用）

拆解卡已按此契约实施；epic 定义结果卡区时可直接采用这四条：

- **结果驱动 · 调用者无关**：卡订阅「**这个工件**」这个状态（如「这条源视频的拆解结果」），**不订阅「谁触发了它」**。同一工件，无论**节点动作**产出还是 **Agent 工具调用**产出，落回**同一张卡**——绝不因触发者不同各开一张（对齐拆解 v1 的 R-C-5/R-C-7）。

- **collapse ≠ unmount · 双向状态保持**：卡收起是**折叠不是卸载**。勾选进度、滚动位置、进行中的 Run，收起再展开后**原样还在**，两个方向（卡→折叠、折叠→卡）都不丢状态。

- **宽度用 `assistantWidth` 单一真相源**：结果卡区宽度 = 现役右栏宽度真相源 `assistantWidth`（`src/workbench/workbenchStore.ts` 默认 340、clamp 300–600）→ `--generation-assistant-target-width`。**不自立第二个宽度数字**（#251 的 520px 已作废）。

- **走查验收断言可发现性 + 几何可见**：卡的验收不只断「DOM 里有没有」，还要断「**用户看得见、点得到**」——控件在视口内、几何可见、可发现（对齐设计系统 §1.6 控件交互契约与走查坑单「expectAbsent 会过早通过 / 控件被 overflow 裁出视口」的教训）。

## 边界声明

- 本意见书是**拆解线的输入**，不是右槽终局的最终裁决书。**右槽终局定义权归 M 线交互 epic。**
- 拆解卡**已按上述结果卡契约实施**（v1 只做「节点动作」这一个入口，但状态键已按「源视频维度」建好，为 M 线的「Agent 会话入口」留对接缝）。
- **epic 若调整细节**（结果卡区的排布、折叠交互、卡与会话流的视觉关系等），**拆解卡随契约搬移**——它订阅的是工件状态、不绑面板 open 布尔，所以能平移进 epic 定义的结果卡区而不返工。
