## 🟢 可落地

### EntityBench：跨镜实体一致性的三柱评测框架，代码已开源

- **链接 / 日期**：[arXiv 2605.15199](https://arxiv.org/abs/2605.15199)，v1 **2026-05-14**；Ruozhen He、Meng Wei、Ziyan Yang、Vicente Ordonez。**代码公开**：[github.com/Catherine-R-He/EntityBench](https://github.com/Catherine-R-He/EntityBench)，12 star。
- **一句话洞察**：唯一针对「跨镜实体（角色 + 物体 + 场景）同时追踪」的公开 benchmark，140 集 2491 镜，recurrence gap 最长 48 镜（= 真实电影难度）；三难度分级（easy/medium/hard，最多 50 镜 / 13 个角色 / 8 个场景 / 22 个物体同时跨镜）。评测三柱分离：帧内质量、prompt 跟随、跨镜一致性——关键是有 **fidelity gate**（只有准确渲染过实体外观的镜头才进跨镜打分，防止「把错的拿去比对」导致假高分）。配套 EntityMem（预存实体可视参考的记忆库），声称 character fidelity Cohen's d = +2.33 vs 现有方法。
- **落到哪个模块**：`evals/journeys/j4-reference.mjs`（参考图旅程）+ `evals/lib/vbenchRubric.mjs`（新增 EntityBench 三柱维度）。Nomi 生成输出只需按 `<results_dir>/<episode_id>/<scene>_<shot>.mp4` 命名喂进评测脚本即可；三柱独立可分批跑（--pillar cross_shot 单跑跨镜部分不占帧内质量 GPU 时间）。与 08-12 GroundShot 调度契约 + 08-17 EM-Vid 实体索引**合并一次落地**，不要三个独立工单。
- **诚实边界**：EntityBench 的 fidelity gate 本身需要一个参考生成（先跑一次让模型渲染实体，再比对后续镜头），冷启动需额外一轮生成预算。12 star 偏低但代码已过可跑验证；EntityMem 是一个参考实现不是 Nomi 必须接的架构。

### StreamEdit：training-free V2V 流式视频编辑，Apache-2.0，代码已开源

- **链接 / 日期**：[arXiv 2605.21466](https://arxiv.org/abs/2605.21466)，v1 **2026-05-20**，v2 **2026-06-30**；Guanlong Jiao 等，project：[dsl-lab.github.io/StreamEdit](https://dsl-lab.github.io/StreamEdit/)。**代码公开**：[github.com/DSL-Lab/StreamEdit](https://github.com/DSL-Lab/StreamEdit)，Apache-2.0，**21 star**；支持 Self Forcing 和 LongLive 两个后端。
- **一句话洞察**：把视频编辑重新定义为「source-conditioned noise-to-data」而非传统的「data-to-data」——用 dual-branch 快速采样（self-attention bridge + cross-attention grounding）在 few-step 流式生成中注入源视频条件，保留结构同时执行文字驱动的局部编辑。演示支持 470 帧 / 30 秒以上长视频；FiVE-Bench（100 视频 420 条编辑案例 6 类编辑）上有系统评测；model-agnostic。本轮升级为 🟢（此前在 08-17 观察列表，当时未确认代码）。
- **落到哪个模块**：`evals/journeys/j5-edit-export.mjs`（时间轴编辑旅程）。具体改法：① 在 j5 旅程里增加 3 条「真实用户编辑任务」（换颜色 / 换主体 / 局部 inpaint），用 StreamEdit 的 FiVE-Bench 6 类编辑标准对结果打分；② 把评分维度接进 `evals/lib/vbenchRubric.mjs` 的结构保留维度（与 08-17 V2V-Bench 的「结构保留 + 布局遵循 + 内容保留」三维合并）。实现层不必接 StreamEdit 的权重，只借它的**评测框架和编辑分类**，Nomi 用现有生成后端跑编辑再打分。
- **诚实边界**：StreamEdit 依赖 Self Forcing 或 LongLive 权重（Hugging Face 可下），如果要在 Nomi 内部真正执行编辑（而非只做评测框架参考）需要接这两个后端；目前 Nomi 走供应商 API，可落地的是**评测范式**，不是运行时替换。21 star 偏低，需持续观察社区反应。

## 🟡 架构教训

### KathaTrace + STG：跨场景「语义轨迹坍塌」的诊断协议

- **链接 / 日期**：[arXiv 2607.01312](https://arxiv.org/abs/2607.01312)，v1 **2026-07-01**；Jamuna S. Murthy、Amin Karimi Monsefi、Rajiv Ramnath。数据集：KathaBench-25K（5000 个叙事 / 20000 个转场 / 28712 个问题）。代码：论文中未提及。
- **一句话洞察**：提出 **Semantic Trajectory Gap（STG）** 指标，专门测量「转场时语义丢失了多少」——用三个条件（仅文本 / 仅图像 / 文图结合）测同一个转场，当「图像条件存在但语义分数反而变差」时，说明视觉连贯掩盖了叙事断裂（看起来流畅但意思接不上）。配套 **Semantic Compass** 修复探针：在生成后用 KathaTrace 信号筛选更优的 storyboard。
- **影响 Nomi 哪个决策**：直接影响 `shotVerifyJudge.ts` 的判断维度。Nomi 当前的 shotVerify 主要做视觉一致性（角色像不像、构图像不像），**没有叙事语义层**——镜头视觉上连贯但前后剧情意思断掉，当前会放行。STG 的教训：shotVerify 应增加「叙事语义延续性」维度，问「这个镜头和上一个镜头的故事在同一条逻辑线上吗」，而不只问「视觉上一不一样」。与 08-17 MuSS 的 ACP-Var 教训（一致性不是越强越好，也不能过弱）结合：**shotVerify 是一个三维区间**：视觉相似度（双向）× 语义延续性（下限）× 动作多样性（下限）。无代码，目前只取诊断框架，不接 benchmark 数字。
- **诚实边界**：STG 的计算依赖 KathaTrace 的三条件对比测试，Nomi 做简化版只需在 shotVerifyJudge 里对每个转场多问一条「语义接续」判断（走 VLM 打 0/1），不必重现整套协议。数据集 25K 公开状态待核实。

### PACR-Video：轻量适配器 + 递归 prompt bank 的多镜外推，无需微调

- **链接 / 日期**：[arXiv 2607.06481](https://arxiv.org/abs/2607.06481)，v1 **2026-07-07**；Anna Córdoba 等，Institution 未明。**暂无公开代码**。
- **一句话洞察**：冻结扩散 transformer，外挂低秩时序适配器（LoRA 型），用「shot-role prompt token」区分「这个镜头在叙事中扮演什么角色（开场 / 过渡 / 高潮 / 收尾）」；维护递归 prompt bank，按预测的叙事依赖关系动态路由「哪些历史镜头的实体/场景/动作信息对当前镜头有用」。适配器组合策略：早期镜头重视觉一致、后期镜头重事件推进和视角变化。
- **影响 Nomi 哪个决策**：「shot-role token」的概念直接对应 Nomi storyboard 里每个镜头的叙事功能标注。Nomi 目前的拆镜头 agent 生成「镜头描述」但没有明确标「这是第几幕的哪类镜头」。教训：拆镜头规划师应在输出的镜头结构里加一个 `role` 字段（`establish / transition / climax / close`），让后续 context routing 可以按镜头功能而不只按顺序取历史上下文。这不需要适配器，只需改 storyboard JSON schema 和镜头 agent 的 prompt。落到：storyboard 规划师的输出 schema（待查文件）。无代码，取设计思路。
