# Nomi 论文雷达 · 2026-08-02

> **检索窗与方法**：按固定 8 个方向检索近 6 个月 arXiv，并用 arXiv 官方 API 倒排核对 2026-07-28 至 07-30 的 cs.CV 新提交；与 2026-08-01 及更早雷达去重。进入正文的条目均回到 arXiv 原文、官方项目页、官方仓库或官方数据页核对日期、任务边界、代码/权重状态和 Nomi 真实落点。

## 一句话总结

本轮 **🟢 0 / 🟡 2 / 🔵 1**。没有新的黑盒 provider 即插能力；最强信号反而落在 Nomi 已经押注的 3D 导演台上：**CinemaTraj** 证明“自由文本 → 可组合的原子运镜 → 几何约束校验”比单个运镜枚举或自由 prompt 更可靠，**VideoCoCo** 则把“可执行灰模过程 → 生成模型重绘”做成了开源系统，并且连不调模型的版本也能提升物理一致性。Nomi 已经有 3D 场景、轨迹、灰模 MP4 与 `video_ref` 链路，缺的不是再造一个 3D 编辑器，而是把这条链从“单段相机运动”推进到“可组合、可校验的导演过程”。

**本轮最该动的两件事：**

1. **先把复合运镜变成结构化计划，不再让词表外意图直接退化成 prompt。** 当前 `cameraMoveBuilder.ts` 的 `CameraMoveSpec` 一次只承载一个 `move`，`create_camera_move` 遇到甩镜/连续复合运镜就走 `customMove` 文本降级；但 `Scene3DState` 本身已经支持多条 trajectory / binding。借 CinemaTraj 的做法，下一步应先定义最小 `camera plan = [{target, move, shot, elevation, duration}]`，让“推近 A → 弧移到 B → 拉远揭示环境”能在同一条灰模 take 内执行，并在渲染前检查主体可见、路径碰撞和目标覆盖。Nomi 是人工搭好的简化 3D 场景，不需要照搬它昂贵的 RGB-D 重建与 256³ SDF。

2. **把 3D 灰模从“相机怎么走”升级为“事情怎么发生”，但只做 Nomi 已有 primitive 能确定表达的小范围。** VideoCoCo 的关键增益来自先生成完整、可检查的过程草稿，再交给视频模型重绘；Nomi 已有 `poseTrack`、locomotion、对象轨迹、离屏录 take 和自动挂 `referenceVideoUrls`，结构上已经过半。应先做走路、坐下、递物、碰撞/跌落等可由现有 primitive 表达的 4–5 个语义关键状态，并在中间帧验“结果不能早于原因出现”；不要把它扩成通用物理模拟器。

## 🟢 可落地（这周/这月能直接进 Nomi）

**本轮无新增。**

VideoCoCo 虽然已开源 agent skills、推理补丁和 8 个 toy triplet，且官方仓三天约 65 stars，但完整效果依赖 OmniWeaving 视频编辑器与其 LoRA/权重；CinemaTraj 只有论文与项目页、尚无官方代码。因此二者都足以指导 Nomi 架构与小样验证，但还不能诚实写成“拿来即接”的 provider 能力。

## 🟡 架构教训（影响设计决策，非即插即用）

### 1. CinemaTraj：自由文本先拆成原子运镜计划，再用真实 3D 几何把“会拍”与“拍得到”合在一起

- **链接 / 日期**：[arXiv 2607.26910](https://arxiv.org/abs/2607.26910)，v1 **2026-07-29**；[官方项目页](https://cinematraj.github.io/)。团队来自 TUM 与 Huawei Dresden Research Center；有完整论文、项目页和 50 个 ScanNet++ 场景实验，但截至本轮未发现官方代码仓，成熟度定 🟡。
- **一句话洞察**：LLM 不直接吐逐帧相机坐标，而是读一个只保留“房间包含什么、物体贴不贴墙/天花”的轻量 3D scene graph，把意图拆成 `anchor → orbit/pan/tilt/dolly/zoom/crane/static → arc transition` 的结构化命令；参数化轨迹再经碰撞/遮挡优化。这样既保留电影术语的语义，又不让相机穿墙、丢目标。
- **证据**：它用三档输入分别测“用户已指定物体+运镜”“只指定物体”“只说抽象气氛”，并用 Motion MSE、文本-轨迹 CLaTr、Collision Rate、Occlusion Rate、Object Coverage 五轴评估；完整系统在除 collision rate 外的指标上均优于基线。消融显示，去掉 anchor selector 会拍错对象，去掉参数化 primitive 路径会变得杂乱，去掉几何优化则会穿家具/遮住主体。
- **影响 Nomi 哪个决策**：
  1. `src/workbench/generationCanvas/nodes/scene3d/cameraMoveVocab.ts` 已有 13 个原子运镜；真正缺口不在继续加 enum，而在“**把多个 primitive 组合成一个有目标的导演计划**”。
  2. `cameraMoveBuilder.ts` 当前一个 spec 只建一条 trajectory + binding，且默认围绕原点静态主体；可把 builder 的输入提升为 plan steps，逐段生成 trajectory/binding，复用 `scene3dTypes.ts` 已有数组结构与 `cameraMoveSchedule.ts` 的确定性采样。
  3. 几何约束先做 Nomi 尺寸适配：用现成 `scene3dSafeFrame.ts` 的投影/AABB 检查主体是否在安全画幅，再对场内 prop/墙做采样碰撞与 raycast 遮挡；不引入 ScanNet++、RGB-D 重建或 SDF 优化重资产。
  4. `evals/journeys/j6-camera-move.mjs` 除现有“选对单个 enum / 产出 mp4 / 喂入 video_ref”外，应新增复合指令的 step 顺序、目标覆盖、全程不出画三项；这比只让 VLM 看“像不像某种运镜”更可诊断。
- **诚实边界**：论文针对已重建的静态室内 3D 场景，Nomi 是简化灰模 staging；它的 collision-free 结论不能直接外推到生成模型最终成片，也不证明所有复合运镜 provider 都会照搬灰模视频。可迁移的是结构化计划与渲前约束，不是整套重建系统。

### 2. VideoCoCo：把“过程”先做成可执行灰模视频，再让生成模型负责外观

- **链接 / 日期**：[arXiv 2607.27380](https://arxiv.org/abs/2607.27380)，v1 **2026-07-29**；[官方代码](https://github.com/micky-li-hd/VideoCoCo)；[官方权重页](https://huggingface.co/mickyhimself/VideoCoCo)。来自 CUHK / USTC / HKU / PKU / SJTU / CMU / THU 等联合团队。官方仓本轮核对约 **65 stars / 2 forks**，已放出 3 个核心 agent skills、推理补丁和 8 个 hand-checked toy cases；README 标注 tuned weights 仍在上传，热度高、但发布状态未闭环。
- **一句话洞察**：文本只描述“要发生什么”，通常没说明整个过程每一时刻怎样演化；VideoCoCo 让 agent 先产一份 physical-state plan（4–5 个语义关键状态、连续变化、因果约束、must-show / must-avoid），再写 Blender 程序渲成白模过程视频，最后才由视频编辑模型重绘成真实外观。**中间件是可执行、可看、可验的，不是另一段更长的 prompt。**
- **关键结果**：在 PhyGenBench 上，OmniWeaving 基线平均 0.475；只把可执行草稿直接喂给未调优编辑器也升到 **0.506**，LoRA 版本到 **0.558**。在 VBench-2.0 物理维度上，平均从 **52.18% 升到 77.88%**。这说明收益不全来自训练，灰模过程本身就提供了生成模型原来缺失的时序约束。
- **影响 Nomi 哪个决策**：
  1. Nomi 现有 `CameraMoveCaptureHost.tsx` / `takeRecording.ts` 已能把 3D 过程录成 mp4，`attachCameraMoveToTarget.ts` 已能挂到目标节点 `referenceVideoUrls`，`j6-camera-move` 也已有真实 provider 验证；**基础传输链不是缺口**。
  2. 当前 `cameraMoveBuilder.ts` 明写“主体在运镜里不动”，所以灰模主要表达 camera path，不能表达“角色先走到桌边、再拿起物品、最后递给 B”的因果过程。`scene3dTypes.ts` 已有 `poseTrack`、locomotion 与 object trajectory，可先在 `stagingBuilder` / take 录制链上增加一个受限 semantic-state plan 编译器，禁止直接做通用 Blender-code agent。
  3. eval 不能只验首帧和末帧。可在 `evals/loop/poseLane.mjs` 或独立 process lane 抽 K0–K4 中间帧，逐条检查 `must_not_show` 和 before/after 因果；例如“递物完成”不得在“接触发生”之前出现。VideoCoCo 官方 planner 的最大价值正是把这些验收条件显式化。
- **诚实边界**：论文主战场是物理过程，不是传统剧情表演；官方完整栈依赖 Blender、OmniWeaving 与专用编辑权重，许可证也随 Tencent HY 组件约束。Nomi 应借“可执行过程草稿”这条原则，并只扩已拥有确定性 primitive 的动作，不应把产品方向拐成重型物理模拟平台。

## 🔵 对标基准（接进 eval 体系自评 Nomi）

### MEDit-Bench：同一批素材，叙事意图不同，正确初剪本来就应该不同；LLM 两两裁判存在严重位置偏差

- **链接 / 日期**：[arXiv 2607.25300](https://arxiv.org/abs/2607.25300)，v1 **2026-07-28**；[官方项目页](https://ogatakatsuya.github.io/medit-bench/)；[官方数据](https://huggingface.co/datasets/kattyan/MEDit-Bench)。大阪大学与 CyberAgent 团队。官方数据本轮核对可下载，约 56 downloads / 1 like；数据是 **annotations-only** 的 72 KB parquet，CC BY-NC-SA 4.0，不重新分发源视频。
- **一句话洞察**：自动剪辑不是“找最精彩片段”——同一条 7–18 分钟素材，用户说“表现兔子的复仇”或“表现角色的成长”，该选的片段、铺垫和顺序会不同。MEDit-Bench 为 60 条长视频配 180 个 message，由 3 位专业编辑分别产出 540 份 cut-only 编辑；同一 message 的跨编辑 F1-Avg 为 0.42，而同一素材不同 message 只有 **0.15**，证明“编辑意图”不是装饰性 prompt，而是选择函数的一部分。
- **评测教训**：它以 union temporal IoU 衡量全局覆盖，再以 cut-level F1 衡量切点数量与位置；同时发现 LLM-as-a-judge 做成片偏好比较有严重 presentation-order bias，即使交换 A/B 顺序也不能稳定裁决。对于创意剪辑，单一 VLM 总分不能当真相源。
- **怎么接进 Nomi eval**：
  1. 当前 `src/workbench/generationCanvas/agent/sendStoryboardToTimeline.ts` 的“一键拼片”只按 `shotIndex` 顺序 append，`TimelinePanel.tsx` 也明确把它定义成初剪主线；先做离线 **message-conditioned arrange lane**，输入同一组已生成 shots + 不同叙事目标，期望选择/顺序发生合理变化，而不是立刻改用户 UI。
  2. 用 `TimelineClip.startFrame/endFrame/offset*` 与 `timelineEdit.ts` 现成边界实现 coverage-tIoU + cut-F1；主指标是可复算的时间边界，VLM 只做解释性诊断，不能单独决定 pass/fail。
  3. 官方任务是“从一条长源视频中选 cut”，Nomi 当前主要是“把已生成镜头排成故事”，任务并不等价。因此第一步只迁移 **message 条件 + 多参考编辑 + 时间边界指标**，用 Nomi 自己的小样集校准；不能直接声称 MEDit-Bench 分数等于 Nomi 成片质量。
- **数据边界**：Hugging Face 仅提供 60 个源视频的 YouTube ID/URL 与 540 行时间段标注，不含视频文件；公开数据卡把行定义为 message × annotator 的 temporal segments。若接 eval，需单独处理源视频可用性、版权与非商用许可，不能把数据打进产品包。

## 8 个固定方向覆盖

| 方向 | 2026-08-02 增量结论 |
|---|---|
| 1. 跨镜角色身份一致 | CineWeaver（2607.26529）提出 shot-routed references + anchor memory，方向贴合 Nomi 的“参考归属 + canonical 锚”，但它要改 Wan2.1/Phantom 的 RoPE、attention 与 VAE decoding，官方仍是 **Code soon**，无法进入黑盒 provider；不重复计数。 |
| 2. Agent 分镜/导演编排 | **新增 VideoCoCo（🟡）**：把过程计划做成可执行草稿；比纯文本 CoT 更可检查。CinemaTraj 的 structured command 也证明 LLM 应输出受约束导演 plan，而不是逐帧坐标。 |
| 3. 运镜/机位/相机轨迹 | **新增 CinemaTraj（🟡）**：原子运镜组合 + 目标 anchor + 几何约束，直指 Nomi 单枚举/自由文本之间的断层。TARS（2607.28261）能按景别/视角/第一第三人称重拍，但需两阶段训练，官方 GitHub 目前只有 README/assets、约 2 stars，无权重/推理代码，筛掉。 |
| 4. 多镜叙事一致性/转场 | CineWeaver 与 FreqForcing（2607.27110）都用模型内部 attention/anchor 抑制长程漂移；前者代码未放，后者需 Self-Forcing 内部 KV/attention，均越过 Nomi provider 边界。本轮无黑盒新落点。 |
| 5. 视频生成 benchmark/eval | FilmBench/FilmOps 仍是导演意图执行主尺；本轮新增的 MEDit-Bench 归到“叙事剪辑”而非生成画质，不与 FilmBench 重复。 |
| 6. Prompt 优化/结构化改写 | 无独立新增。CinemaTraj / VideoCoCo 的共同教训是：复杂时空意图不该只改写成更长 prompt，而应编译成可执行结构。 |
| 7. 音频/唇形同步/TTS | Ripple（2607.26818）用跨模态 recurrent memory 做 28 FPS 联合音视频长生成，但需三阶段训练/蒸馏/RL，未见 Nomi 可接的开放 provider 或独立 lipsync 组件，筛掉。 |
| 8. 视频编辑/inpaint/关键帧 | **新增 MEDit-Bench（🔵）**：message-conditioned cut 选择 + tIoU/cut-F1 + LLM judge 位置偏差。TARS 属重拍模型而非本地编辑组件；Explicit Layer Modeling 等需要训模型，本轮不收。 |

## 上轮 vs 本轮 diff

- **新增**：CinemaTraj（2607.26910，🟡）、VideoCoCo（2607.27380，🟡，官方代码/skills/推理补丁）、MEDit-Bench（2607.25300，🔵，公开时间段标注）。它们都在 07-28 至 07-30 提交、但 08-01 雷达正文未收。
- **主线变化**：08-01 的 FilmBench 告诉 Nomi“该怎样判导演意图有没有执行”；本轮 CinemaTraj + VideoCoCo 补上“怎样把导演意图变成可执行、可校验的中间过程”。两轮合起来形成闭环：**意图 → 结构化 3D 过程 → 灰模参考 → 生成 → 电影语言/过程指标验收**。
- **延续不重复**：GroundShot 的 canonical 身份锚、FilmWorld/VideoWeaver 的有状态编排、FilmBench 的电影语言 eval 仍成立。CineWeaver/FreqForcing 的 anchor memory 再次印证这些方向，但没有跨过 Nomi 的黑盒 provider 边界，故不重复进三档。
- **过期方向：无。**
- **本轮筛除约 10 篇**：重复的 ShotPlan/ShotStream/FilmBench，需模型内部 attention/latent 的 CineWeaver、FreqForcing、TPD、Temporal Concentration，以及需训练且无成熟接入面的 TARS、Ripple、Visko Orbis / Explicit Layer Modeling 等。
