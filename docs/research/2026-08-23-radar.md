# Nomi 论文雷达：2026-08-23

一句话：视频生成质量的下一步不是继续堆 prompt，而是把“实体记忆、相机/主体运动分离、镜头级诊断”接到通用意图和真实用户任务上。

本轮最该动的两件事：

1. 用 EntityBench/VBench 的细粒度维度给 Nomi 的参考图和镜头任务建立基线；
2. 把 DirectorBench 的“按瓶颈诊断”思路变成用户能理解的下一步建议，而不是单一质量分。

## 🟢 可落地

### EntityBench：跨镜实体一致性

- 日期：2026-05-14
- 来源：[论文](https://arxiv.org/abs/2605.15199)、[代码与数据](https://github.com/Catherine-R-He/EntityBench/)
- 洞察：实体再次出现的间隔越长，一致性下降越明显；显式 per-entity memory 对角色 fidelity 和 presence 最有效。
- 落到 Nomi：参考图不是一次性上传字段，而是角色/道具/场景实体的可验证记忆；为 J2/J4 记录实体在镜头间的保持率。

### DirectorBench：长片质量要定位瓶颈

- 日期：2026-05-28
- 来源：[论文](https://arxiv.org/abs/2605.30090)、[代码](https://github.com/jiaminchen-1031/DirectorBench)
- 洞察：长片生成应分剧本、视觉、音频、跨模态和稳定性维度，并结合用户偏好和 checkpoint，而不是压成一个总分。
- 落到 Nomi：`shotVerify`/质量门返回“哪一项失败、下一步改什么”，例如“角色通过，相机偏差，建议减小运动复杂度”。

## 🟡 架构教训

### MotionCtrl：相机运动和主体运动要分开

- 日期：2023-12-06（SIGGRAPH 2024）
- 来源：[论文](https://arxiv.org/abs/2312.03641)、[官方实现](https://github.com/TencentARC/MotionCtrl)
- 洞察：相机和主体是两个独立的控制条件；混在同一条“运动强度”里会使用户无法知道究竟改了什么。
- 影响 Nomi：`ShotIntent` 分开保存 `cameraIntent` 和 `subjectMotion`；供应商不支持独立控制时标记 translated，而不是假装 native。

### Wan / Diffusers：能力要模块化声明

- 日期：2025-03-21 / 持续维护
- 来源：[Wan 论文](https://arxiv.org/abs/2503.20314)、[Wan 代码](https://github.com/Wan-Video/Wan2.1)、[Diffusers](https://github.com/huggingface/diffusers)
- 洞察：不同 pipeline、scheduler 和 control input 是可组合模块；模型之间不是一套固定参数。
- 影响 Nomi：公共合同只存通用意图和明确 override，适配器根据 `provider + model + mode` 生成原生请求。

## 🔵 对标基准

### VBench / VBench++：细粒度单镜头质量

- 日期：2023-11-29 / 2024-11-20
- 来源：[VBench](https://arxiv.org/abs/2311.17982)、[VBench++](https://arxiv.org/abs/2411.13503)、[项目页](https://vchitect.github.io/VBench-project/)
- 怎么接：作为单镜头底层维度，至少记录主体一致性、运动平滑、时间闪烁、空间关系和 prompt alignment；不要用总分替代这些维度。
