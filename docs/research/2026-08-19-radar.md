## 一句话总结

本轮 **🟢 7 / 🟡 8 / 🔵 3**，筛掉约 45 篇噪音。真正的信号只有一条：**音频那块，开源终于追上来了**——MOVA（1.1k star、Apache-2.0、权重已放、**360p 在 4090 上跑得动**）让「Nomi 导出的视频是哑巴」这个缺口第一次有了不违背本地优先路线的补法。其余大部分是「思路可借、东西没放出来」。

**复核推翻的两条（子代理搜到但说错了，别照抄）**：
- **UnityShots** 不是「有官方实现」——仓库里**只有 README**，checkpoints / 训练码 / agent 系统全标着 "released soon"。降到 🟡，只能当设计参考。它宣称的「3–9 镜头」也不在摘要里，摘要说的是 200 条多镜序列的 benchmark。
- **Lip Forcing** 能下载的是 **14B 学生权重**；论文卖点那个 31 FPS 实时的 **1.3B 学生标着 "coming soon"**。想要实时的，现在拿不到。

**本轮最该动的两件事：**

1. **拿 MOVA 补「导出视频无声」这个缺口。** 这是本轮唯一「真缺口 × 真开源 × 本地跑得动」三者同时成立的东西：Apache-2.0、MOVA-360p / 720p 权重都在 HuggingFace、推理 12–48GB VRAM（官方明说 RTX 4090 可跑 8 秒 360p，只是不建议在 4090 上训），已有社区 ComfyUI 节点。对 Nomi 的意义是它**一次推理同时出画面 + 对口型的语音 + 音效 + BGM**，不用拼三套系统。先跑 demo 评估质量，再决定接生成节点还是接导出后处理。**注意边界**：与 Veo 3 / Sora 2 仍有差距；多说话人声纹区分未充分验证。
2. **把节点 prompt 从一坨字符串升级成结构化字段**（参照 Script-a-Video 的 MTSS 四流：Reference 实体状态 / Shot 镜头语言 / Event 动作序列 / Global 全局上下文）。这条**不依赖任何人的权重、不花训练算力、纯工程**，Nomi 自己就能做完，且直接打「跨镜身份」这个命门——现在每镜的参考信息埋在自由文本里，模型得自己猜哪句是身份约束；拆成显式字段后，跨镜复用哪些、每镜换哪些，一目了然。落到：画布节点的 prompt 数据模型（具体文件待核实）。**注意边界**：论文数字是在 HunyuanVideo 上测的，换模型幅度未知，代码未开放，要自己实现。

## 🟢 可落地

### MOVA：开源唯一的「画面 + 声音一次出」，且 4090 跑得动 ✅已复核

- **链接 / 日期**：[arXiv 2602.08794](https://arxiv.org/abs/2602.08794)，v1 **2026-02-09**；OpenMOSS（SII-OpenMOSS，40 人）。
- **代码**：[github.com/OpenMOSS/MOVA](https://github.com/OpenMOSS/MOVA)，**1.1k star**，**Apache-2.0**。已放：MOVA-360p / 720p 权重（HuggingFace）、推理码、训练与 LoRA 微调脚本、评测码、Streamlit 工作流。
- **一句话洞察**：32B MoE（推理激活 18B），单次推理原生同时产出视频 + 同步音频（对口型语音 / 音效 / BGM），自称多语种唇同步 SOTA。开源侧此前没有真正做视频音频联合生成的重量级工作。
- **落到哪**：Nomi 导出无声。两个接法二选一——① 生成节点上加「一键带声生成」；② 导出前的后处理。建议先跑 demo 评质量再选。
- **诚实边界**：8 秒 360p 推理 12–48GB VRAM（视 offload 策略），官方明说**不建议在 4090 上训练**（推理可以）；质量与闭源商业模型有差距；多说话人声纹区分未充分验证；>60s 未测。

### Lip Forcing：V2V 唇同步，但能拿到的是 14B 不是那个实时的 1.3B ✅已复核

- **链接 / 日期**：[arXiv 2606.11180](https://arxiv.org/abs/2606.11180)，v1 **2026-06-09**；KAIST AI + AIPARK。
- **代码**：[github.com/cvlab-kaist/LipForcing](https://github.com/cvlab-kaist/LipForcing)，**111 star**，**Apache-2.0**。已放：推理码（streaming / segmentwise 两种）、两阶段训练码、**14B 学生权重**（2026-07-07 首发）。**1.3B 学生权重与 Gradio demo 仍在 roadmap，未发布。**
- **一句话洞察**：首个 V2V（视频进视频出）的自回归扩散唇同步——把 14B 双向扩散教师蒸馏成因果学生，每段 2 步去噪。V2V 这个形态对 Nomi 比 image-driven talking head 更顺：不破坏角色已有的肢体动态。
- **落到哪**：已生成角色视频 + 配音 → 唇形对齐版本，作为预览/导出阶段的后处理。
- **诚实边界**：**论文卖点的实时（1.3B / 31 FPS）现在下不到**，能跑的 14B 不是为实时设计的；需要输入侧已有基础视频；极端侧脸/遮挡未测；用户侧 MacBook 跑不动，要云化。

### JoyAI-Video-Edit：指令式改已生成的视频，815 star / Apache-2.0

- **链接 / 日期**：[arXiv 2608.03974](https://arxiv.org/abs/2608.03974)，v1 **2026-08-04**；JD.com。
- **代码**：[github.com/jd-opensource/JoyAI-Video-Edit](https://github.com/jd-opensource/JoyAI-Video-Edit)，**815 star**，Apache-2.0，代码 + checkpoint 已公开。（未二次核验）
- **一句话洞察**：16B 自回归扩散，因果生成（不等未来帧、不预设时长），720p@30FPS 实时跑在单张 B200；支持主体替换 / 局部修改 / 换背景 / 风格迁移 / 运动修改 / 参考引导编辑。
- **落到哪**：Nomi 现在对已生成节点不满意只能整条重生成。这个能做「让角色把手放下」「背景换成雪天」这类指令式局部修改，省掉重生成全镜头的成本。
- **诚实边界**：实时要 B200，A100 上会降速；16B 推理成本不低；>60s 长镜漂移待实测。

### CineCap：把参考片段自动翻译成电影语言，喂回 prompt

- **链接 / 日期**：[arXiv 2606.24636](https://arxiv.org/abs/2606.24636)，v1 **2026-06-23**；作者机构待核实。
- **代码**：[github.com/Hectormxy/CineCap](https://github.com/Hectormxy/CineCap)，9 star；权重 `CineCap-GRPO-8B` 已上 HuggingFace，训练/推理/评测码完整。（未二次核验）
- **一句话洞察**：GRPO 微调的 8B 多模态 LLM，对视频输出专业摄影术语描述（运镜/景别/景深/构图角度）。
- **落到哪**：用户拖进一个参考片段 → 自动产出「中景，固定机位，主体在右三分之一，浅景深，由右向左横摇」→ 并进生成 prompt。补的是「用户说不清自己想要什么镜头」这个摩擦。star 少但代码 + 权重齐，成熟度高于 star 数。
- **诚实边界**：CineCap-Bench 仅 472 对，评测规模小；8B 本地约需 16GB VRAM；产出的是 caption，要做 prompt 增强还差一步格式桥接。

### Script-a-Video（MTSS）：结构化 prompt 四流分解

- **链接 / 日期**：[arXiv 2604.11244](https://arxiv.org/abs/2604.11244)，v1 **2026-04-13** / v2 04-15；Tencent Hunyuan。**暂无公开代码**。（未二次核验）
- **一句话洞察**：把「一大段叙述文字」换成 Reference（实体状态）/ Shot（镜头语言）/ Event（动作序列）/ Global（全局上下文）四条流，再用 relational grounding 显式绑定镜间身份与时序。论文数字：身份一致性 +45%。
- **落到哪**：见「最该动的第 2 件」。training-free，纯 prompt 格式层工程。
- **诚实边界**：数字在 HunyuanVideo 上测的，跨模型幅度未知；无代码要自己实现；音频对齐部分与 Nomi 无关。

### VQQA：生成完自动质检 + 改 prompt 重试的闭环

- **链接 / 日期**：[arXiv 2603.12310](https://arxiv.org/abs/2603.12310)，v1 **2026-03-12**；Google Cloud AI Research。**代码未开放**（项目页 All rights reserved）。（未二次核验）
- **一句话洞察**：QG agent 自动出视觉问题 → QA agent 用 VLM 作答给质量报告 → PR agent 把报告当「语义梯度」改 prompt。黑盒调用不改模型，T2V-CompBench +11.57%。
- **落到哪**：节点生成后自动问 5 条视觉问题（人物在不在 / 动作对不对 / 运镜方向对不对），不达标自动改 prompt 重生成，最多 3 轮。比人工逐帧看快，比 VBench 静态打分有行动力。
- **诚实边界**：没开源，逻辑得自己写；QG 的问题质量直接决定成败，问歪了 PR 就跑偏；每轮多 1–2 次 VLM 调用，有成本。

### TriMotion / SymphoMotion：运镜控制，两个都代码权重齐全

- **TriMotion**：[arXiv 2606.20774](https://arxiv.org/abs/2606.20774)，**2026-06-18**，ECCV 2026；GIST + Huawei + Yonsei + Imperial。[github.com/seunghyuns98/TriMotion](https://github.com/seunghyuns98/TriMotion)，9 star，含训练/推理码 + 权重 + Motion Triplet Dataset（136K）。把视频 / pose / 文本三种轨迹描述映射进同一 motion embedding，训一次三种输入通吃，底座 Wan2.1。
- **SymphoMotion**：[arXiv 2604.03723](https://arxiv.org/abs/2604.03723)，v1 **2026-04-04** / v4 06-24，CVPR 2026；CUHK-SZ + SJTU 等。[github.com/grenoble-zhang/SymphoMotion](https://github.com/grenoble-zhang/SymphoMotion)，**106 star**，推理+训练码、HF 权重、RealCOD-25K 数据集。相机轨迹 + 物体运动联合控制，2D 视觉引导 + 3D 轨迹嵌入双通道，避免两者互相干扰。
- **落到哪**：Nomi 拆镜头产出的机位描述是文本（「缓慢推近 + 右移」），TriMotion 的 text→camera 路径直接对得上；SymphoMotion 对「角色走向 A 点同时镜头弧形推近」这类联合控制。两者都有代码权重，可在 ComfyUI 里先接通验证。
- **诚实边界**（均未二次核验）：TriMotion 9 star 传播度低，训练数据是 UE5 合成，真实风格泛化待评；SymphoMotion 需要同时准备两条控制信号（3D 物体轨迹实际制作中不易拿到），多人复杂交互未知。

## 🟡 架构教训

### UnityShots：双槽记忆的思路对口，但东西没放 ⚠️已复核降档

- **链接 / 日期**：[arXiv 2606.21661](https://arxiv.org/abs/2606.21661)，v1 **2026-06-19**；Jiehui Huang、Yuechen Zhang、Bin Xia、Xin Tao、Pengfei Wan、Jiaya Jia 等（复核确认作者名单）。
- **代码**：[github.com/JIA-Lab-research/UnityShots](https://github.com/JIA-Lab-research/UnityShots)，92 star，CC BY-NC 4.0——**但仓库里只有 README + 项目页，checkpoints / 训练码 / agent 系统全标 "released soon"**。子代理原报「有官方实现」，实测不成立。
- **一句话洞察**（摘要原文核对过）：两个固定大小的槽——**LTM 锚定开场镜头、STM 持有紧邻的上一镜尾部**，每次切镜由一个「边界条件门」更新，该门融合视觉切点概率与节拍信号。配套发布 200 条多文化多镜序列的 benchmark。（子代理说的「3–9 镜头」不在摘要里，存疑。）
- **影响哪个决策**：这正是 Nomi 现在最高频的手工摩擦——用户得自己把上一镜的尾帧截图传给下一镜。LTM/STM 双槽给出的结构是：**开场帧锚全局、尾帧接局部，两者分开存、在切点处才刷新**。Nomi 可以在画布节点层用纯工程实现这个语义（节点 A 生成后自动缓存尾帧、开场节点的首帧另存），不需要它的权重。**这条今天就能设计，不用等它开源。**
- **诚实边界**：CC BY-NC，商用要联系作者；更长序列的累积漂移未测；训练素材是电影级，与 AI 生成视频的风格分布有差异。

### 其余教训（均未二次核验，只取思路）

- **Co-Director**（[2604.24842](https://arxiv.org/abs/2604.24842)，2026-04-27，Google）：四 agent 分层 + 多臂老虎机全局探索，**用 MLLM 评估整个 keyframe 序列而不是单帧**来抓 identity drift。对 Nomi 可立即实验的是后半句——拆镜完成、视频生成前，先用 VLM 对一批 keyframe 做整体一致性检查，发现漂移提前打断，比生成后再检测便宜得多。代码只有 demo 级。
- **A²RD**（[2605.06924](https://arxiv.org/abs/2605.06924)，2026-05-07）：完全 training-free 的 Retrieve-Synthesize-Refine-Update 四步循环，与 Nomi 的节点执行同构。无 GitHub，只有项目页；底座绑 Veo 3.1 + Gemini 3 Flash；一致性提升数字来自自评 MLLM judge，可信度待第三方确认。
- **VideoMemory**（[2601.03655](https://arxiv.org/abs/2601.03655)，2026-01-07，HKUST + ByteDance）：Dynamic Memory Bank 的 retrieve-then-update。[代码](https://github.com/EnVision-Research/VideoMemory) 9 star、CC BY-NC-SA、基于 LangGraph、强依赖 Sora-2 + Nano-Banana 2 API。**注意 2601 已在窗口边缘**，benchmark 仅 54 case。价值在读它的 Memory Bank 数据结构，不在跑它。
- **SLVMEval**（[2603.29186](https://arxiv.org/abs/2603.29186)，2026-03-31，CVPR 2026）+ **JudgeFit**（[2606.22918](https://arxiv.org/abs/2606.22918)，2026-06-22）：两篇都在说同一件事——**别无条件相信 VLM-as-judge**。SLVMEval 发现现有评测系统在 9/10 个维度不如人类，语义/时序一致性差距最大；JudgeFit 发现不同 VLM 对同一标准的理解差异巨大，强行统一评分标准反而放大偏差，按 VLM 分别校准能提升约 32% 人类相关度。**对 Nomi 的直接后果**：如果要做自动质检（见上面 VQQA），语义一致性这类维度必须保留人工抽检，且多 VLM 投票前得先分别校准，不能直接平均。
- **Gloria**（[2603.29931](https://arxiv.org/abs/2603.29931)，CVPR 2026）：用一组 anchor 帧紧凑表示角色外观替代「每镜重传参考图」。无代码、需在 DiT 主干内训练。启发的是 UI 层——项目初始化时上传一次 anchor 图集，后续每镜自动注入。
- **ARGUS**（[2606.11670](https://arxiv.org/abs/2606.11670)，Kuaishou）：把多视角参考图拼成 3×3 马赛克再注入。无代码、绑 WAN。**但「多参考图拼成一张」这个想法零成本可试**——Nomi 调 API 常只能传 1 张图，把 3 张角色视角拼成 2×2 传进去，值得做一次对照实验。
- **FLEX**（[2602.14027](https://arxiv.org/abs/2602.14027)）/ **EffectErase**（[2603.19224](https://arxiv.org/abs/2603.19224)，CVPR 2026）/ **MTV-Inpaint**（[2503.11412](https://arxiv.org/abs/2503.11412)）/ **OrthoMotion**（[2606.22835](https://arxiv.org/abs/2606.22835)）/ **VERTIGO**（[2604.02467](https://arxiv.org/abs/2604.02467)，ECCV 2026）/ **DiFlowDubber**（[2603.14267](https://arxiv.org/abs/2603.14267)，CVPR 2026）/ **PhyPrompt**（[2603.03505](https://arxiv.org/abs/2603.03505)）：均**无可用代码**，只取思路，等开源。其中 OrthoMotion 是单作者小会议 poster，可信度需保留。

## 🔵 对标基准

- **MSVBench**（[2602.23969](https://arxiv.org/abs/2602.23969)，2026-02-27）：首个专为**多镜头**生成设计的分层 benchmark（global priors → scene segments → shot conditions），Spearman 与人类 94.4%。核心论断值得记：当前模型是「视觉插值器」而非「世界模型」，长程稳定性是最大短板。**暂无公开代码**，先把它的三层分解当 spec 用。
- **FilmBench**（[2607.24241](https://arxiv.org/abs/2607.24241)，2026-07-27，北京电影学院）：1169 条提示词全部从获奖影片逆向工程，其中 1056 条是多镜头；3 轴 / 12 组件 / 35 子指标，与 90 位电影学院评委 Spearman 0.95。**FilmOps 算子已开源**（[github.com/Neo-yk/FilmOps](https://github.com/Neo-yk/FilmOps)，27 star，Apache-2.0），数据集在 HuggingFace。**怎么接**：拿它的多镜提示词当 Nomi 的压测集，别自己手写测试 prompt。注意它的提示词代表「最理想的提示质量」，不代表 Nomi 真实用户会怎么写。
- **WorldReasonBench**（[2605.10434](https://arxiv.org/abs/2605.10434)，2026-05-11）：[代码](https://github.com/UniX-AI-Lab/WorldReasonBench) 23 star、MIT、含 6000+ 专家标注偏好对。测的是「画面逼真 ≠ 世界推理正确」。对 Nomi 当前阶段价值中等（我们的痛点是跨镜一致而非物理因果），但那 6000 对偏好数据将来可用来训「哪个候选版本更合理」的偏好模型。

## 上轮 vs 本轮 diff

- **新出现的主题**：音频/唇同步这条线本轮第一次有了真开源可跑的东西（MOVA / LipForcing），此前一直标着「Nomi 唇形同步暂无」的缺口有了候选解。
- **状态变化**：
  - **MSAVBench**（2605.20183，08-15 提过）：GitHub [ali-vilab/MSAVBench](https://github.com/ali-vilab/MSAVBench) 已建但仅 4 star，README 的 TODO 显示 prompt 数据 / 参考资源 / 评测码**仍待发布**——比 08-15 当时以为的更不可用。
  - **DirectorBench**（2605.30090，08-18 收录）：HuggingFace 数据集已上线，GitHub 代码仍未公开，无重大变化。
- **降权提醒**：本轮 🟡 里大半是「无代码」。这个比例连续几轮偏高，说明按「有没有代码」筛比按「方法新不新」筛更省时间——下轮把「有可运行代码」提到筛选第一关。

**本轮筛掉约 45 篇噪音**，主因分三类：① 日期出窗（arxiv id < 2602，占一半以上）；② 无代码 + 方法与已收录条目高度重叠；③ 方向偏离（纯图像序列故事可视化、embodied agent、纯画质 SOTA、纯综述）。
